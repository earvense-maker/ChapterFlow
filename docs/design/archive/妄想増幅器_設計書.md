作成日: 2026-08-14  
対象: ChapterFlow v0.1.0-beta.9 以降  
状態: 実装前  
実装後の扱い: 実装と受け入れ完了後、`docs/design/archive/` へ移動する。

## 0. この文書の目的

本書は、ChapterFlow に「妄想増幅器」を追加する実装エージェント向けの正本である。

妄想増幅器は第3の作品形式ではない。既存の `novel` と `roleplay` を表現形式として再利用し、その上に次の機能を追加する別軸の体験モードである。

- 場面生成後に毎回3〜5個の「次に楽しめそうな方向」を提示する。
- ユーザーは選択肢、自由記述、「この場面に留まる」から次を選ぶ。
- 選択、自由記述、お気に入り、再生成、編集などを観測事実として保存する。
- AIは観測事実から、ユーザーの欲望について自然言語の暫定仮説を更新する。
- 暫定仮説を次の場面と選択肢へ反映し、理解・増幅・探索のループを作る。

本書で明記していない既存挙動は変更しない。特に通常の小説・通常のロールプレイ、既存プロジェクト、既存保存データの互換性を守る。

## 1. プロダクト原則

### 1.1 優先順位

妄想増幅器では次を優先する。

> 体験 ＞ 整合性  
> 欲望 ＞ 物語としての正しさ  
> 探索 ＞ 完成

設定や長期記憶を捨てるのではない。矛盾によって没入が壊れることを防ぐために使う。軽微な不整合より、現在の場面の魅力を優先する。

### 1.2 成功条件

主要な成功条件は次の2点である。

- この続きをもう一度見たくなったか。
- 自分でも気づいていなかった好みに出会えたか。

セッション時間や生成回数だけを成功指標にしない。長時間利用を目的化せず、理解の精度、明示的なお気に入り、新しい方向の発見を評価する。

### 1.3 人間理解の扱い

嗜好メモはユーザーの真実や心理診断ではない。AIが現在持っている創作体験上の仮説である。

悪い解釈:

> ユーザーは愛情不足である。甘えが好きである。

望ましい解釈:

> 普段は自立している人物が、安心できる相手の前だけ無自覚に少し幼くなる落差への反応が強い可能性がある。露骨に甘える方向はこれまで選ばれていない。

原因を断定せず、「次にどのような体験を試す価値があるか」へ変換する。

## 2. 決定済み仕様

1. `ProjectType` は `novel | roleplay` のまま維持する。
2. プロジェクトへ別軸の `experienceMode: standard | amplifier` を追加する。
3. 妄想増幅器の新規作成では、最初に小説またはロールプレイを選ぶ。
4. 作成は既存の「一文から始める」クイックセットアップを流用する。
5. 希望者は既存の詳細設定へ移り、人物、関係、舞台、守ることなどを記述できる。
6. ロールプレイではユーザーの分身として体験する。
7. 小説では三人称で人物と関係を眺める。
8. 毎ターン3〜5択と自由記述を提示する。
9. 複数選択専用UIは作らない。「AとBを混ぜたい」は自由記述で扱う。
10. 「この場面に留まる」と「別の方向を出す」は常設操作にする。
11. グローバル学習は妄想増幅器の標準機能としてオンにする。設定からオフにできる。
12. グローバル学習オフ時は、既存グローバルメモを生成へ使わず、新しいグローバル観察も保存しない。作品内・現在の学習は継続する。
13. 作品削除時、抽象化済みのグローバル理解は残す。作品内の生ログは作品とともに削除される。
14. 嗜好分析は通常画面へ露出しない。設定画面で任意に閲覧・修正・削除できる。
15. 再生成案は履歴として残す。本格的な分岐世界線ツリーはMVPに含めない。

## 3. スコープと用語

### 3.1 三つの理解スコープ

嗜好理解は固定プロフィールではなく、次の三スコープで持つ。

1. `global`: 作品をまたいで繰り返し現れる比較的持続的な理解。
2. `project`: この人物・関係・世界に固有の理解。
3. `current`: 直近数ターンで強い一時的な欲求。

生成時の優先順位は原則として次の通り。

```text
current ＞ project ＞ global
```

ロールプレイの会話枠は独立した嗜好階層ではない。`current` の文脈キー・保存単位として利用する。新しい会話枠では `current` を空から始め、`project` と `global` を引き継ぐ。

小説には会話枠を作らない。`current` は同じ作品内の直近場面と選択から連続的に更新する。アプリ終了や日付変更をセッション境界にしない。

### 3.2 視点の区別

グローバル理解では少なくとも次を混同しない。

- `roleplay`: 分身として体験したいこと。
- `novel`: 三人称で眺めたいこと。
- `mixed`: 両方で繰り返し確認されたこと。

「嫉妬が好き」のように視点を失った保存を避ける。メモ本文にも、誰の立場で何を体験・観察したい可能性があるかを書く。

### 3.3 ハード境界

避けたい要素はAI推論による嗜好仮説と分離し、ユーザーが書いた自然言語のハード境界として扱う。

- グローバル境界: どの妄想でも避ける。
- 作品内境界: この作品では避ける。

探索候補も境界を越えてはならない。境界は `current/project/global` の嗜好メモより常に優先する。

## 4. 基本UX

### 4.1 新規作成

作品一覧へ「妄想増幅器を始める」を追加する。

```text
妄想増幅器を始める
├─ ロールプレイとして体験する
│  └─ 既存「一文からキャラとの会話を始める」へ
└─ 小説として眺める
   └─ 既存「一文から物語を始める」へ
```

クイックセットアップには次を表示する。

- 見たい人物・関係・感情を表す一文。
- 絶対に守ってほしいこと（任意）。
- 最初に見たい場面または会話の舞台（任意）。
- 「詳細を自分で決める」導線。

セットアップセッションへ `experienceMode` を保持し、クイックセットアップから詳細設定へ移っても失わない。コミット時はモデル出力を信用せず、セッションの `experienceMode` を `CreateProjectBody` へ強制反映する。

セットアップのlocalStorage復元キーと「最新activeセッション」の探索条件にも `experienceMode` を含める。同じ `purpose=novel` でも、通常作品の相談を妄想増幅器の入口から誤復元してはならない。

妄想増幅器プロジェクトは高速な反復を優先するため、生成後の自動設定レビュー `refineAutomation` を初期値 `off` で作成する。ユーザーが作品設定から明示的に有効化した場合だけ既存処理を使う。採用後のstory stateやcontext summaryなど、生成をブロックしない既存派生処理は従来どおり利用してよい。

### 4.2 初回説明

最初に妄想増幅器を開始するときだけ、次を簡潔に説明する。

- 選択や自由記述から、作品をまたいで好みの仮説を更新する。
- 仮説は設定画面で閲覧・修正・削除できる。
- グローバル学習は設定からオフにできる。
- 関連する仮説は、選択したモデルプロバイダーへ生成材料として送られる。

初期値はオンとする。説明確認は `amplifierDisclosureVersion` としてアプリ設定へ保存し、説明文が重要変更されたときだけ再表示する。

### 4.3 場面後の共通UI

生成された本文またはキャラクター応答の下に次を表示する。

- 3〜5個の方向カード。
- 自由記述欄。
- 常設「この場面に留まる」。
- 常設「別の方向を出す」。これは本文ではなく選択肢だけを作り直す。
- 「ここ好き」。場面全体をお気に入りにする。
- 文章選択時の「ここ好き」。一文・台詞・仕草をお気に入りにする。
- 任意の「この方向は違う」。理由は自由記述できるが必須にしない。

方向カードには自然な見出しと短い説明だけを表示する。「鉄板」「変奏」「冒険」や分析語は表示しない。

選択肢生成中は本文を操作・閲覧できる。「次の方向を考えています…」と表示し、失敗時は本文を保持したまま「方向を再取得」を表示する。

選択肢は、保存済みの実効本文が確定してから作る。小説のNG自動書き換え、手動編集、履歴復元、下書き切替が本文を変えた場合は旧turnをsupersededにし、新しい改訂へ選択肢を作り直す。ロールプレイの初回greetingもキャラクターメッセージとして保存済みなら同じ対象にする。

### 4.4 小説の進行

方向カード、自由記述、「留まる」のいずれかを送ると、現在表示中の下書きを暗黙に採用し、その方向で次の場面を生成する。

処理順:

1. 表示中の `turnId` とアンカーが最新か検証する。
2. 専用advanceサービスが選択を `InteractionEvent` として冪等保存する。
3. 同じproject lock内で、アンカーが現在選択中の下書きであることを再検証し、既存 `acceptGeneration` と同じ規則で採用する。
4. `pendingAdvance` leaseを保存してproject lockを離す。
5. leaseのoperationIdを付けて既存小説生成を開始する。別の通常生成・advanceはleaseがterminalになるまで409で拒否する。
6. 次場面の保存後、advanceをcompleteにし、新しい選択肢を非同期生成する。

次場面生成に失敗しても、選択済みの現在場面は採用状態のまま残す。advanceをfailedとして保存し、同じoperationIdから「同じ方向で再試行」できるようにする。同じイベントを二重記録せず、別方向へ変更する場合だけ旧advanceをcancelledにして新イベントを作る。

既存の「この案を採用」「書き直す」「前の案」「次の案」は残す。妄想増幅器では方向選択が採用を兼ねるが、手動確認・復元も可能にする。

### 4.5 ロールプレイの進行

妄想増幅器の選択や自由記述は、通常のユーザーメッセージではなく「今回見たい方向」として保存する。メタ方向を「あなた」の発言バブルへ混ぜない。

- 選択肢は分身の行動・台詞、相手側から起きてほしいこと、場面全体の感触を混在できる。
- 選択された分身の行動・台詞だけは、今回明示的に許可された内容として生成してよい。
- AIは選択されていない重要な行動、台詞、決断を分身へ追加しない。
- 自由記述内の引用された台詞は分身の台詞として扱い、それ以外は方向指示として扱う。

標準ロールプレイの `messages-stream` 契約は維持する。妄想増幅器用には、turn、選択内容、clientEventIdを受け、InteractionEvent保存からキャラクター応答までを扱う専用ストリーム経路を追加する。

既存 `runTurn` の `send/regenerate` へ条件分岐を散らさず、内部のturn種別へ `amplifier` を追加する。

- `beginTurn(kind=amplifier)`: session revision、active、in-flight、interactionと最新アンカーを検証する。user messageは保存しない。
- `buildTurnPrompt`: 保存済み方向を `amplifierDirection` として渡す。
- `commitTurn`: character messageだけを追加し、`amplifierInteractionId`を付け、session revisionを1増やす。
- 生成失敗: messagesを変更せず、同じinteractionから再試行可能にする。

## 5. 選択肢の生成方針

### 5.1 本文生成と分離する

本文・キャラクター応答と選択肢を同じLLM応答へ混ぜない。

理由:

- 既存の小説とロールプレイはプレーンテキスト・ストリーミング契約を持つ。
- JSONトレーラーを混ぜると本文漏出、パース失敗、停止時の不整合が起きる。
- 選択肢生成に失敗しても、成功した本文を失ってはならない。

本文または応答を保存した後、短い非ストリーミング呼び出しで選択肢を作る。共通の `modelGenerationService.runNonStreaming` を利用し、アダプター分岐や認証再読込を複製しない。

### 5.2 候補構成

3〜5件の中に、文脈に応じて次を含める。

- `exploit`: 既知の好みを満たす候補。
- `variation`: 好きな構造を保った変奏。
- `explore`: 許可範囲内の隣接する未知を試す候補。

通常は `explore` を最低1件含めるが、明示された現在欲求やハード境界と衝突する場合は無理に入れない。「留まる」は常設操作なので3〜5件を消費しない。

`strategy` は生成制御と評価用の非表示メタデータであり、欲望の分類ではない。表示文は場面内の自然な言葉にする。

### 5.3 初期状態

学習初期は知ったふりをしない。互いに異なる感触を持つ候補を広く出し、選択が蓄積するにつれて `exploit` の比率を増やす。

### 5.4 出力契約

モデルには純JSONを要求し、サーバーで厳格に正規化する。

```json
{
  "exploit": [
    { "label": "もう少し近づく", "description": "相手の本音が行動から少しだけ漏れる。" }
  ],
  "variation": [
    { "label": "別の表情を見る", "description": "同じ距離感のまま、意外な弱さを覗かせる。" }
  ],
  "explore": [
    { "label": "空気を少し崩す", "description": "小さな予想外で二人の反応を試す。" }
  ]
}
```

正規化規則:

- 合計3〜5件。
- `label` は1〜40文字、`description` は1〜160文字。
- 空、重複、境界違反候補を除外する。
- `choiceId` と `turnId` はモデルに作らせずサーバーで採番する。
- パース失敗時は修復呼び出しを最大1回だけ行う。それでも失敗したら `failed` とし、本文を維持して再試行UIを出す。

## 6. 欲望についての観察ノート

### 6.1 原則

欲望そのものをタグや独立数値へ分解しない。

```text
行動ログ = 観測された原資料
PreferenceMemo = AIが現在持つ自然言語の解釈
ユーザー修正 = AI解釈への明示的な訂正
```

構造化するのは、識別、適用範囲、時刻、根拠、更新競合、ユーザー修正など、プログラムが管理する外枠だけとする。

### 6.2 PreferenceMemo

```ts
export type PreferenceScope = 'global' | 'project' | 'current';
export type PreferenceAppliesTo = 'novel' | 'roleplay' | 'mixed';
export type PreferenceConfidence = 'tentative' | 'recurring';

export interface PreferenceMemo {
  memoId: string;
  scope: PreferenceScope;
  appliesTo: PreferenceAppliesTo;
  text: string;
  confidence: PreferenceConfidence;
  evidenceEventIds: string[];
  counterEvidenceEventIds: string[];
  revision: number;
  updatedAt: string;
}
```

制約:

- `text` が中心であり、嗜好タグ配列や「無邪気さ: 0.8」のような軸は追加しない。
- `confidence` は確率ではなく成熟度である。数値化しない。
- 根拠IDは代表的なものを最大20件保持する。全処理位置は別のカーソルで管理する。
- `confidence` はAI解釈の成熟度だけを表す。ユーザーの明示的な訂正や境界は、下記のCorrectionまたは境界データとして別に保持する。

### 6.3 メモ長とプロンプト優先度

MVPの保存上限目安:

- `current`: 800文字。
- `project`: 1,600文字。
- `global` の各視点: 2,000文字。

生成プロンプトへ全量が入らない場合は `current`、`project`、関連する `global` の順に優先する。無関係な視点のグローバルメモは送らない。

### 6.4 ユーザー修正を別レイヤーにする

AIメモ本文を直接ユーザー確定文へ変えるだけでは、メモ全体が更新不能になるか、次のAI更新で修正箇所が消える。ユーザーの訂正はAIメモと分けて保持する。

```ts
export interface PreferenceCorrection {
  correctionId: string;
  scope: PreferenceScope;
  appliesTo: PreferenceAppliesTo;
  text: string;
  status: 'active' | 'withdrawn';
  revision: number;
  createdAt: string;
  updatedAt: string;
}
```

設定画面の「修正」は、AIメモを破壊的に上書きするのではなくactiveなCorrectionを作る。Desire InterpreterはactiveなCorrectionを常に読み、AIメモの残りを更新する。ユーザーが修正を解除した場合だけ`withdrawn`にする。`memo_corrected`イベントには修正前後とcorrectionIdを残す。

設定画面では「AIの現在の理解」と「あなたが訂正したこと」を区別して表示する。両者を結合した実効メモだけを生成プロンプトへ渡す。

## 7. InteractionEvent

### 7.1 目的

InteractionEventは嗜好解釈ではなく、ユーザーが実際に行った操作の追記専用ログである。後から解釈をやり直せることを優先する。

```ts
export type AmplifierInteractionType =
  | 'choice_selected'
  | 'free_text'
  | 'stay'
  | 'choice_alternatives_requested'
  | 'favorite'
  | 'direction_rejected'
  | 'scene_regenerated'
  | 'content_edited'
  | 'memo_corrected';

export interface AmplifierInteractionEvent {
  schemaVersion: 1;
  eventId: string;
  clientEventId: string;
  sequence: number;
  projectId: string;
  contextKey: string;
  mode: 'novel' | 'roleplay';
  type: AmplifierInteractionType;
  turnId?: string;
  anchor: AmplifierAnchor;
  payload: unknown;
  excludeFromGlobalLearning: boolean;
  createdAt: string;
}
```

`payload` はイベント種別ごとの判別共用体として実装し、API境界で検証する。任意オブジェクトをそのまま保存してはならない。

### 7.2 保存する文脈

選択イベントでは、選んだ項目だけでなく提示されていた選択肢集合を `turnId` 経由で復元できるようにする。自由記述は原文を保存する。お気に入りは場面アンカーと選択範囲の抜粋を保存する。

単なる閲覧時間、スクロール量、ウィンドウ滞在時間はMVPの学習信号にしない。

### 7.3 信号の解釈

固定点数の合計で嗜好を決めない。概ね次の順で証拠として扱う。

```text
明示的な「ここ好き」・ユーザー修正
  ＞ 繰り返された自由記述
  ＞ 単発の自由記述・選択
  ＞ 再生成・編集
  ＞ 未選択
```

再生成は「嫌い」だけでなく別案への好奇心の場合がある。未選択は比較対象として保存するが、1回の未選択を否定と解釈しない。

### 7.4 イベントの作成経路

| type | 作成API・処理 | clientEventId | payloadの要点 | 順序 |
|---|---|---:|---|---|
| `choice_selected` | novel/roleplay advance | 必須 | choiceId | advance開始前に保存 |
| `free_text` | novel/roleplay advance | 必須 | 自由記述原文 | advance開始前に保存 |
| `stay` | novel/roleplay advance | 必須 | 固定command | advance開始前に保存 |
| `choice_alternatives_requested` | turn alternatives | 必須 | 旧turnId | 新turn作成前に保存 |
| `favorite` | favorites API | 必須 | whole/selection、anchor、抜粋 | お気に入り保存と同じproject lock |
| `direction_rejected` | interactions API | 必須 | turnId、任意理由 | alternatives作成前に保存 |
| `scene_regenerated` | 既存再生成成功後のhook | サーバー採番 | before/after anchor | 新案保存後に追記 |
| `content_edited` | 既存編集・復元成功後のhook | サーバー採番 | anchor、before/after hash | 本文保存後に追記し旧turnをsupersede |
| `memo_corrected` | preference修正API | 必須 | correctionId、修正前後 | Correction保存と同じlock |

APIから受けるイベントはすべてpayload判別共用体を検証する。既存サービスの成功hookで作るイベントは、元の編集・再生成が失敗した場合に記録しない。

## 8. AmplifierTurnとアンカー

### 8.1 型

```ts
export type AmplifierAnchor =
  | {
      kind: 'novel';
      generationId: string;
      textRevisionNumber: number;
    }
  | {
      kind: 'roleplay';
      sessionId: string;
      messageId: string;
      contentRevision: number;
    };

export interface AmplifierChoice {
  choiceId: string;
  strategy: 'exploit' | 'variation' | 'explore';
  label: string;
  description: string;
}

export interface AmplifierTurn {
  schemaVersion: 1;
  turnId: string;
  projectId: string;
  contextKey: string;
  anchor: AmplifierAnchor;
  anchorTextHash: string;
  anchorExcerpt: string;
  status: 'choices_pending' | 'ready' | 'failed' | 'consumed' | 'superseded';
  choices: AmplifierChoice[];
  supersedesTurnId?: string;
  consumedByEventId?: string;
  errorCode?: string;
  revision: number;
  createdAt: string;
  updatedAt: string;
}
```

`contextKey` はクライアント入力から採用せず、サーバーで次の規則により作る。

- 小説: `novel:main`
- ロールプレイ: `roleplay:<sessionId>`

sessionIdは既存のsafe path segment検証を通す。ロールプレイ会話のアーカイブ後もメモは履歴として残すが、新しい会話へcurrentメモを引き継がない。

### 8.2 古い選択肢の拒否

選択時は、アンカーIDだけでなく本文改訂番号とハッシュを検証する。本文編集、別案への移動、再生成、別セッションへの切替後に古いカードが押された場合は `409 amplifier_turn_stale` を返す。

revision欠損は既存互換どおり`0`と解釈する。hashは保存済み実効本文をUTF-8文字列として、改行だけLFへ正規化し、trimや空白圧縮をせずSHA-256で計算する。選択肢prepare、commit、押下検証で同じ純関数を使う。

`clientEventId` はクライアントで採番する。同じIDの再送は既存イベントを返し、二重記録・二重進行を防ぐ。

### 8.3 別の方向

「別の方向を出す」は現在ターンを消さない。新しいターンを `supersedesTurnId` 付きで作り、旧ターンを `superseded` にする。本文・応答は変更しない。この操作自体は弱い信号として記録するが、旧候補への明示的な拒否とは扱わない。

## 9. 保存構造

### 9.1 作品内

```text
projects/<projectId>/amplifier/
├─ interactions.jsonl
├─ notebook.json
├─ notebook-revisions.jsonl
└─ turns/
   └─ <turnId>.json
```

- `interactions.jsonl`: 追記専用の生ログ。
- `notebook.json`: 現在の `project` メモ、文脈キーごとの `current` メモ、ユーザーCorrection、解釈カーソルと状態。
- `notebook-revisions.jsonl`: メモ更新・ユーザー修正の版履歴。
- `turns`: 選択肢とアンカー。本文再生成とは別に履歴を保持する。

`interactions.jsonl` を `state.json` や `RoleplaySession.messages` へ埋め込まない。無制限成長するログによって毎回の状態読み書きを重くしないためである。

`notebook.json` には肥大化しない運用状態として、解釈状態のほか小説advanceのleaseを最大1件だけ保持できる。

```ts
interface PendingNovelAdvance {
  operationId: string;
  interactionEventId: string;
  sourceTurnId: string;
  acceptedGenerationId: string;
  status: 'reserved' | 'generating' | 'complete' | 'failed' | 'cancelled';
  resultGenerationId?: string;
  errorCode?: string;
  leaseExpiresAt: string;
  revision: number;
  updatedAt: string;
}
```

期限切れleaseは次回操作のpreflightで`failed`へ正規化する。失敗・期限切れでもinteractionと採用済み場面は消さない。

### 9.2 グローバル

```text
config/amplifier/
├─ global-notebook.json
├─ global-notebook-revisions.jsonl
└─ global-observations.jsonl
```

グローバルファイルは `DATA_DIR/config` 配下に置く。プロジェクト削除と独立し、データ保存先の移動・バックアップには含まれる。

`global-observations.jsonl` には場面全文や自由入力原文を複製しない。作品内の解釈から得た、自然言語の抽象観察、視点、成熟度、元イベント参照だけを保存する。これにより作品削除後も抽象化済み理解を再解釈できる。

`globalLearningEnabled` と `globalLearningResetAt` は、グローバルデータの利用可否・再学習境界を決める同一のプライバシー状態である。どちらも `%APPDATA%` 側のapp-settingsではなく `global-notebook.json` に保存し、データ保存先の移動・バックアップ・復元と一緒に移ることを保証する。新規作成時の `globalLearningEnabled` は `true` とする。初回説明の確認版 `amplifierDisclosureVersion` だけは端末UI状態としてapp-settingsに保存してよい。

`global-notebook.json` のトップレベルには最低限 `globalLearningEnabled`、`globalLearningResetAt`、メモ、Correction、解釈カーソル、revisionを持たせる。オン・オフAPIはこのファイルをグローバルmutex下で更新し、app-settingsへ二重保存しない。

作品削除後、参照元イベントが存在しない場合はUIで「元の作品は削除済み」と扱う。グローバルメモや観察を自動削除しない。

### 9.3 ストレージ契約

`ProjectStorage` に作品内・利用者全体の両方の操作を追加し、`PROJECT_STORAGE_METHODS`、`fileProjectStorage`、bound facade、契約テストを同時更新する。

グローバル保存も `UserContext` に属する。Electron MVPではローカル固定利用者だが、将来のWeb版で全利用者が同じグローバルファイルを共有しない契約にする。

### 9.4 JSONL耐障害性

- 追記は `withDataDirWrite` と専用サービスロックを通す。
- 読み込み時は最終行の途中書き込みや破損行を個別に隔離し、正常行を失わない。
- `sequence` はプロジェクト単位で単調増加させる。
- ノート本体は `safeWriteJson` で置換する。
- グローバル更新には専用mutexを持つ。

## 10. Desire Interpreter

### 10.1 責務

Desire Interpreterは場面を生成しない。InteractionEvent、提示候補、直前場面の必要な抜粋、以前のメモから観察ノートを書き直す。

LLMへの指示:

- 単独タグへ分解せず、関係・状況・変化・表現方法の組み合わせを保つ。
- 観測された事実と、その説明仮説を区別する。
- 別の説明可能性と反証を検討する。
- 分身として体験したいことと、三人称で眺めたいことを混同しない。
- 心理的原因、病理、人格を診断しない。
- 以前のメモをユーザーの真実として扱わない。
- ユーザー修正済みの記述を勝手に反転しない。
- 次の生成で試す価値のある方向として簡潔にまとめる。

出力はJSONの外枠と自然言語本文にする。欲望タグや数値軸を出力契約へ追加しない。

### 10.2 二速度更新

ユーザーが今選んだ方向は、解釈完了を待たず次の生成へ直接渡す。詳細なメモ更新はバックグラウンドで行う。

更新トリガー:

- 「ここ好き」またはメモ修正: 即時予約。
- 自由記述: current更新を早期予約。
- 3〜5件の未処理イベント蓄積。
- 連続再生成、編集、「この方向は違う」。
- ロールプレイ会話のアーカイブ。
- ワークスペース読み込み時に未処理カーソルが残っている。

更新失敗時:

- 既存メモを維持する。
- 場面生成と選択をブロックしない。
- `pending/failed` 状態と処理カーソルを保存する。
- 次回読み込みまたは設定画面の「再試行」で再開する。

MVPでは別の分析専用モデル設定を作らない。小説ではプロジェクトのactive model、ロールプレイでは会話枠に固定されたmodelを使う。グローバルだけの手動再試行で元プロジェクトがない場合は、アプリ設定の相談用既定モデルを使う。モデルが利用できなければpendingを維持する。

### 10.3 通常更新と再解釈

通常更新は以前のメモと新イベントを統合する。ただし初期解釈の固定化を防ぐため、一定回数ごと、またはユーザー修正時に、以前のAIメモを正解として与えない再解釈を行う。

再解釈では原資料とユーザー修正から新メモを作り、旧メモとの差を比較して保存する。ユーザー修正は常に入力へ含める。

### 10.4 昇格

単一イベントを直接グローバルの確定嗜好へしない。

- まず `current` を更新する。
- 同じ作品で反復または明示確認された観察を `project` へ統合する。
- 複数の独立イベント、反復、明示的お気に入りからグローバル観察候補を作る。
- 他作品でも確認された場合は `recurring` を強める。
- ユーザーが修正・確認した内容はAIメモの成熟度へ混ぜず、authoritativeなCorrectionとして重ねる。

厳密な点数表は作らない。昇格に利用した根拠と反証を保存し、LLMが理由を自然言語で説明できる状態を保つ。

## 11. 生成プロンプト統合

### 11.1 共通レイヤー

小説・ロールプレイの既存プロンプトへ、妄想増幅器有効時だけ次の追加レイヤーを入れる。

1. 固定された妄想増幅器規則。
2. ユーザーが今回選んだ方向または自由記述。
3. `current` メモ。
4. `project` メモ。
5. 関連する `global` メモ。
6. グローバル・作品内ハード境界。

固定規則には次を含める。

> 仕事は物語を効率よく完結させることではない。現在の空想体験を魅力的にし、続きをもう一度見たくなることを優先する。嗜好メモは命令や真実ではなく暫定仮説である。今回の明示的な選択を最優先し、同じ嗜好を機械的に反復しない。現在の場面に魅力があるなら、場所・時間・関係を進めず細部へ留まってよい。軽微な整合性より体験を優先するが、没入を壊す矛盾とハード境界は避ける。

ユーザー入力、メモ、境界、選択肢はすべて既存 `renderDataBlock` 系で引用し、プロンプト内の新しい命令区画として解釈させない。

### 11.2 小説

`promptBuilder` へ妄想増幅器用コンテキストをoptional入力として追加する。通常作品では完全に省略し、生成結果を変えない。

「留まる」はサーバー側で固定指示へ変換する。

- 場所と時間を大きく動かさない。
- 大事件を起こさない。
- 関係を決定的に確定させない。
- 現在の感情を急変させない。
- 会話、仕草、空気、生活の細部を追加する。

### 11.3 ロールプレイ

`buildRoleplayUserPrompt` へoptionalな `amplifierDirection` と嗜好メモを追加する。標準ロールプレイでは省略する。

既存のユーザー行動保護規則を維持し、今回の方向で明示された範囲だけを例外として許可する。選択肢にない分身の重要な決断を補完しない。

### 11.4 プロンプト予算

妄想増幅器用セクションを `PromptBudgetReport` に追加し、縮小順を固定する。

1. ハード境界と今回方向は削らない。
2. `current` を優先する。
3. `project` を要約・切り詰める。
4. `global` を関連部分だけにするか省略する。

予算不足でメモが省略されても生成は続行する。UI通知には秘密やメモ本文を含めず、既存と同じ数値・sectionIdだけを出す。

## 12. 並行処理・整合性

### 12.1 ロック原則

- プロジェクトロックを保持したまま、本文、選択肢、Desire InterpreterのいずれのLLM呼び出しも待たない。
- グローバルロックを保持したまま、プロジェクトロックを取得しない。
- プロジェクト更新を先に確定してロックを離し、その後グローバル観察を更新する。
- グローバル更新失敗によって作品内メモをロールバックしない。

### 12.2 選択肢生成の三段階

1. `prepare`: プロジェクトロック内でアンカー、本文改訂、必要なメモ、境界を読み取る。
2. `generate`: ロック外でLLMを呼ぶ。
3. `commit`: 再度プロジェクトロックを取り、アンカーと改訂が同じ場合だけターンを保存する。変化していれば結果を破棄し `stale` とする。

Desire Interpreterも同じprepare/generate/commit方式を使い、`expectedRevision` と処理カーソルで古い結果の上書きを防ぐ。

### 12.3 冪等性

- `clientEventId` で同じ操作の再送を検出する。
- `turnId + revision` で古い選択を拒否する。
- 生成済み `interactionId` が同じリトライではイベントを増やさない。
- イベントの解釈済み位置は `foldedThroughSequence` で管理する。

## 13. API案

API名は既存の `/api` 配下へ置く。最終的な関数名は既存命名へ合わせてよいが、責務境界は維持する。

### 13.1 プロジェクト内

```text
GET  /projects/:id/amplifier/state?kind=novel
GET  /projects/:id/amplifier/state?sessionId=<roleplaySessionId>
POST /projects/:id/amplifier/turns
POST /projects/:id/amplifier/turns/:turnId/alternatives
POST /projects/:id/amplifier/turns/:turnId/interactions
POST /projects/:id/amplifier/favorites
POST /projects/:id/amplifier/novel/advance-stream
GET  /projects/:id/amplifier/preferences
PUT  /projects/:id/amplifier/preferences
POST /projects/:id/amplifier/preferences/retry
```

`POST /turns` はクライアントから本文を受け取らない。アンカーIDと期待改訂だけを受け、サーバーが保存済み本文を読む。

novel advanceとroleplay amplifier-turn-streamは、次のいずれか一つと`clientEventId`を受け、event作成をadvance開始処理の中で行う。

- `selectedChoiceId`
- `freeText`
- `command: stay`

選択肢のラベル・本文をクライアントから信用しない。`turnId` からサーバー保存値を解決する。

汎用 `POST /interactions` は、生成を開始しない `direction_rejected` の記録に使用する。`alternatives`、`favorites`、preferences修正、既存再生成・編集hookは、それぞれの処理内で対応eventを作る。クライアントが任意のevent typeを直接指定できるAPIにはしない。

### 13.2 小説生成

UIは小説の方向選択で既存`accept`と`generate`を個別に呼ばない。専用 `novel/advance-stream` が、InteractionEventの冪等保存、アンカー再検証、暗黙採用、pendingAdvance予約、次場面生成をオーケストレーションする。

内部的には `GenerateRequestBody` / `GenerationRecord` にoptionalな `amplifierInteractionId` と `amplifierOperationId` を追加してよい。指定時はサーバーが保存済みevent、未完了lease、対象generationが現在選択下書きだったことを検証し、今回方向を解決する。通常の `wish` だけの既存経路は変更しない。

advanceは必ず `prepare/reserve -> generate -> commit` に分ける。`prepare/reserve` ではproject lock内でevent保存、アンカー再検証、暗黙採用、`pendingAdvance` lease予約までを行い、ロックを解放する。本文のモデル呼び出しはロック外で行う。`commit` は再度project lockを取り、operationIdとlease状態を検証して生成結果を保存し、leaseをterminalへ遷移させる。

`pendingAdvance` がterminalでない間、通常の小説生成、別のadvance、採用状態を変える操作はサーバー側で409を返す。期限切れleaseはpreflightでfailedへ遷移させてから再試行を許可する。UIだけのdisabledを排他制御にしてはならない。

生成成功後、`GenerationRecord` にoptionalな `amplifierInteractionId` を保存し、リトライと根拠追跡に使う。

### 13.3 ロールプレイ生成

```text
POST /projects/:id/roleplay/sessions/:sessionId/amplifier-turn-stream
```

入力は `turnId`、turn revision、`clientEventId`、選択・自由記述・stayのいずれか、既存セッション `revision`。`beginTurn(kind=amplifier)` がeventを冪等保存して方向を解決する。通常ユーザーメッセージを追加せず、保存済み方向をプロンプトへ渡してキャラクターメッセージを生成する。保存したキャラクターメッセージへoptionalな `amplifierInteractionId` を持たせる。

### 13.4 グローバル

```text
GET    /system/amplifier-settings
PUT    /system/amplifier-settings
GET    /system/amplifier-preferences
PUT    /system/amplifier-preferences
DELETE /system/amplifier-preferences
POST   /system/amplifier-preferences/retry
```

`DELETE` はグローバルメモ、Correction、版履歴、抽象観察を削除し、現在の `globalLearningEnabled` と新しいreset時刻を持つ空の `global-notebook.json` を再作成する。全消去によってオン・オフ状態を勝手に変えない。作品内の過去イベントは残るが、`globalLearningResetAt`より前のイベントからグローバル理解を復活させない。

### 14.1 アプリ設定

`AppSettingsPanel` に「妄想増幅器・人間理解」セクションを追加する。

## 15. 削除・複製・移行

### 15.1 既存データ

- `experienceMode` 欠損は `standard` と解釈する。
- 既存プロジェクトへ妄想増幅器UIやプロンプトを出さない。
- optionalフィールド追加のため、一括データ移行は行わない。
- API境界では `experienceMode` を必ず正規化して返す。

### 15.2 作品削除

既存どおりプロジェクトディレクトリ全体を削除する。作品内InteractionEvent、turn、project/currentメモは削除される。

`CONFIG_DIR/amplifier` のグローバルメモ、版履歴、抽象観察は削除しない。削除確認ダイアログへ追加選択肢は出さない。これは決定済み仕様である。

ただし妄想増幅器作品の削除確認には、次の趣旨を明示する。

> 作品内の本文・行動ログ・作品内メモは削除されます。すでに抽象化されたグローバル理解は残ります。グローバル理解はアプリ設定から確認・全消去できます。

### 15.3 複製

妄想増幅器プロジェクトを複製した場合:

- `experienceMode` は引き継ぐ。
- 世界、人物、創作契約など既存の複製対象は従来どおり引き継ぐ。
- InteractionEvent、turn、project/currentメモ、ロールプレイセッションは複製しない。
- 新プロジェクトはグローバルメモだけを参照し、作品内理解は空から始める。

### 15.4 全消去後の再学習

グローバル理解の全消去後、古い作品ログを再走査して自動復活させない。`globalLearningResetAt` より後に生じたイベントだけを新しいグローバル学習対象にする。

## 17. 実装順序

以下はすべてMVPを構成する実装スライスであり、学習を後続リリースへ延期する意味ではない。

### Slice 0: ドメインと保存

1. `amplifier.ts` 型。
2. `experienceMode` の正規化と互換性。
3. 作品内・グローバル保存パス。
4. ProjectStorage契約。
5. InteractionEventの冪等追記とturn保存。

### Slice 1: 作成導線

1. ProjectListの入口。
2. novel/roleplay選択。
3. QuickSetup/Setupへのmode伝播。
4. commitでamplifier project作成。
5. 初回説明。

### Slice 2: 選択ループ

1. 選択肢生成サービス。
2. AmplifierTurn API。
3. Reader UIと暗黙採用→次場面生成。
4. RoleplayWorkspace UIと専用direction stream。
5. 留まる、別の方向、方向違い。
6. stale/idempotency/再試行。

### Slice 3: 人間理解

1. project/currentメモ。
2. globalメモと抽象観察。
3. Desire Interpreterの非同期fold。
4. 生成プロンプトへの優先度付き注入。
5. 失敗・再起動後の再開。
6. 通常更新と再解釈。

### Slice 4: 明示シグナルと設定

1. 場面全体・選択範囲の「ここ好き」。
2. グローバル・作品内境界。
3. メモ閲覧・修正・削除。
4. グローバルオン・オフと全消去。
5. ロールプレイ会話枠のグローバル学習除外。

### Slice 5: ハードニング

1. parser不正、破損JSONL、途中終了。
2. 競合、stale、二重クリック。
3. プロンプト予算。
4. 既存標準モードの回帰。
5. functional/visual/viewport-fit E2E QA。

### 17.1 リリースゲート

実装量が大きいため、コミットとレビューはSlice単位に分ける。ただし「選択肢だけで学習しないゲームブック」を妄想増幅器MVPとして完了扱いしない。

MVP必須の垂直スライス:

- experienceMode付きのnovel/roleplay作成。
- 両形式の3〜5択、自由記述、留まる、別方向。
- InteractionEventとstale/idempotency。
- current/project/globalの自然言語メモ。
- 非同期Interpreterと生成非阻害。
- 三スコープの生成プロンプト反映。
- グローバル学習オン・オフ、閲覧、修正、全消去。
- 作品削除後のグローバル保持。
- 場面全体の「ここ好き」。

同じ機能完成作業の後段へ分離可能な項目:

- 文章範囲を選択した「ここ好き」。
- ロールプレイ会話枠ごとのグローバル学習除外。
- 通常更新とは別の定期的な全面再解釈。版履歴と手動再解釈APIは先に用意する。
- 詳細な設定画面上の根拠・反証表示。

後段項目を延期してもデータ形式を作り直さず追加できるよう、InteractionEvent、Correction、memo revisionの契約はSlice 0で完成させる。

## 21. 実装時の注意

- `experienceMode` は `projectType` を増やす代わりに使う。`amplifier` を第3のProjectTypeへ追加しない。
- 既存 `Memory` の `preference/negative` をPreferenceMemoの代用品にしない。
- PreferenceMemoをcreative contract、story state、canonへ書き戻さない。
- 本文と選択肢を同じ出力にしない。
- 非同期補助処理の失敗を成功した本文生成の失敗へ変えない。
- LLM呼び出し中にプロジェクト・グローバルの書き込みロックを保持しない。
- モデルが返したchoiceId、eventId、scope、projectIdを信用しない。
- 通常モードのプロンプトへ空の妄想増幅器見出しを追加しない。完全に従来出力を維持する。
- コメントは明白な処理説明ではなく、ロック順、アンカー検証、仮説を真実扱いしない理由など、非自明な意図に使う。

## 22. 最終的な構図

```text
Scene Generator
  入力:
    現在の作品・会話文脈
    今回選ばれた方向
    ハード境界
    current / project / relevant global の観察ノート
  出力:
    次の本文またはキャラクター応答

Choice Generator
  入力:
    保存済みの最新出力
    観察ノートと境界
    直前までに提示した候補
  出力:
    exploit / variation / explore から3〜5方向

Interaction Log
  保存:
    選択、自由記述、留まる、お気に入り、再生成、編集

Desire Interpreter
  入力:
    原資料、以前の観察ノート、ユーザー修正
  出力:
    自然言語による current / project / global の暫定仮説

生成 → 選択 → 観測 → 解釈 → 次の生成
```

設定を理解するAIから、遊んでいる人を理解していくAIへ移行する。ただし理解を固定プロフィールにせず、原資料から何度でも再解釈できる観察ノートとして保持する。
