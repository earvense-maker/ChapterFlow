# 本文・会話履歴の手動編集 設計書

作成日: 2026-08-10
対象バージョン: 未定（0.1.0-beta.11 以降を想定）
実装後の扱い: 実装と受け入れ確認の完了後 `archive/` へ移動する。

## 0. 結論

ChapterFlow に、次の2種類の手動編集を追加する。

1. ロールプレイでは、ユーザー発言・キャラクター発言のどちらも、過去の任意の発言を編集できる。
2. 小説では、draft / accepted の生成本文を編集できる。accepted 本文を編集しても採用状態は維持し、本文から作られた物語状態・潜在設定・文脈要約を再抽出する。

共通原則は「本文が正本、記憶は派生データ」である。画面と通常 API は常に最新版だけを返し、旧版は明示的に「編集履歴」を開いたときだけ表示する。履歴の復元も過去データの削除ではなく、新しい改訂として記録する。

この機能は生成結果の再生成ではない。ユーザーが文章そのものを正し、その訂正を以後の生成・要約・設定抽出へ反映するための機能である。

## 1. 背景

現状にも限定的な置換処理はあるが、一般的な本文編集としては利用できない。

- ロールプレイの `replacePendingMessageId` は、応答前の末尾ユーザー発言だけを置換する停止後の訂正機構である。
- ロールプレイの再生成は、末尾のキャラクター応答を別の応答へ置き換える処理であり、任意発言の手動編集ではない。
- 小説本文は `GenerationRecord.responseText` が生成時の原文となり、NG 表現の局所リライトだけが `text-revision` として追記される。
- accepted 本文から StoryState、潜在設定、文脈要約が派生するため、本文だけを差し替えると表示内容と記憶が食い違う。

このため、UI の textarea だけを追加するのではなく、改訂履歴、楽観的排他、派生データの無効化と再構築を一体で設計する。

## 2. 決定事項

### 2.1 ユーザー確認済み

- ロールプレイのユーザー過去発言も編集対象にする。
- キャラクター発言も編集対象にする。
- 通常表示では修正版だけを見せる。
- 小説の accepted 本文を編集しても accepted のままにする。
- accepted 本文の編集後は、修正版から再抽出する。

### 2.2 本設計で固定する方針

- ロールプレイの後続発言は自動削除しない。過去発言だけを訂正し、以降の会話列は残す。
- 手動編集を理由に generationId、messageId、sceneId を作り直さない。
- 編集は明示的な「保存」で確定し、自動保存はしない。
- 空文字への更新は削除と同義にせず、入力エラーとする。発言・本文の削除機能は別設計とする。
- 手動本文を、契約検査や NG 表現検査が無断で再リライトしない。違反候補は警告だけを返す。
- archived ロールプレイセッションは編集不可とする。

## 3. スコープ

### 3.1 対象

- ロールプレイ発言の最新版表示、編集、履歴閲覧、履歴からの復元
- 小説生成本文の最新版表示、編集、履歴閲覧、履歴からの復元
- accepted 本文の採用維持
- 編集によって古くなった要約、関係性、StoryState、潜在設定の無効化と再構築
- 同時編集・生成中編集・再抽出失敗の安全な扱い

### 3.2 対象外

- 発言やシーンの削除、並べ替え、分割、結合
- 後続会話・後続シーンの自動書き直し
- 複数箇所の一括置換
- リッチテキストエディタ、共同リアルタイム編集
- 旧版同士の高度な差分マージ
- 作品設定へ昇格済みの項目を、会話編集だけで自動削除すること

## 4. 用語と不変条件

- **原文**: 最初に保存された発言または生成本文。
- **改訂**: 原文または直前の最新版に対して保存された手動・自動の変更記録。
- **実効本文**: 原文へ改訂を時系列に適用した最新版。通常 UI、プロンプト、抽出処理が使用する本文。
- **派生データ**: 会話要約、関係性、セッション内潜在設定、StoryState、作品潜在設定、文脈要約。
- **派生状態**: `fresh | pending | stale`。本文の版と派生データの版が一致するかを表す。

次を不変条件とする。

1. 保存成功後、通常 UI と通常 API が返すのは実効本文だけである。
2. 改訂履歴は追記型であり、復元操作でも既存履歴を変更・削除しない。
3. accepted 本文の手動編集で `GenerationStatus` を変更しない。
4. 派生データを `fresh` にするのは、抽出開始時と完了時で本文版が一致した場合だけである。
5. 再抽出失敗を理由に、保存済み本文を旧版へ戻さない。
6. `stale` な派生データを、最新本文から得た情報としてプロンプトへ渡さない。

## 5. 共通の改訂モデル

```ts
type TextRevisionSource =
  | 'manual-edit'
  | 'history-restore'
  | 'ng-auto-rewrite';

interface TextRevisionSummary {
  revisionId: string;
  revisionNumber: number;
  source: TextRevisionSource;
  createdAt: string;
  beforeHash: string;
  afterHash: string;
}
```

- `revisionNumber` は対象テキストごとに 1 から増やす。原文は 0 とする。
- API の更新条件は `expectedRevisionNumber` とし、本文全体をクライアントから比較用に再送しない。
- `beforeHash` / `afterHash` は破損検出と診断用であり、認証用途には使わない。
- 履歴 API だけが旧本文を返す。セッション一覧、ReaderState、生成 API 応答へ旧本文を混ぜない。
- 復元は、選んだ版の本文を新しい `history-restore` 改訂として末尾へ追加する。

## 6. ロールプレイ発言編集

### 6.1 データモデル

ロールプレイはセッション JSON が小さく、セッション単位のロックと安全な JSON 置換が既にある。このため第1実装では、実効本文と履歴を同じセッション JSON に保存し、1回の安全書き込みで原子的に更新する。

```ts
interface RoleplayMessage {
  // 既存項目
  messageId: string;
  role: 'user' | 'character';
  content: string;              // 実効本文
  createdAt: string;

  // 追加
  contentRevision?: number;     // 旧データは 0 と解釈
  editedAt?: string;
}

interface RoleplayMessageRevision {
  revisionId: string;
  messageId: string;
  revisionNumber: number;
  source: 'manual-edit' | 'history-restore';
  beforeContent: string;
  afterContent: string;
  createdAt: string;
}

interface RoleplayDerivedMemoryStatus {
  status: 'fresh' | 'pending' | 'stale';
  sourcePrefixFingerprint: string; // 要約済み prefix の messageId + contentRevision
  editedMessageId?: string;
  updatedAt: string;
  errorMessage?: string;
}
```

`RoleplaySession` に次を追加する。

```ts
messageRevisions?: RoleplayMessageRevision[];
derivedMemoryStatus?: RoleplayDerivedMemoryStatus;
```

`messageRevisions` はサーバー内部データであり、`RoleplaySessionView` の `Omit` 対象へ追加する。通常のセッション取得で履歴本文を漏らさない。

型の `Omit` だけでは実行時の object spread から項目は消えないため、`toRoleplaySessionView` でも `messageRevisions` を明示的に分離して返さない。API 漏えいを確認する回帰テストを追加する。

当面は履歴を削除しない。実測でセッション JSON の肥大化が問題になった場合だけ、同じ API 契約を保ったままセッション別 JSONL へ移す。

### 6.2 保存処理

`editRoleplayMessage` はセッション単位の既存ロック内で次を行う。

1. プロジェクト、セッション、messageId の存在を確認する。
2. セッションが `active` であることを確認する。
3. 同じセッションで応答生成中・要約確定処理中でないことを確認する。
4. `expectedSessionRevision` と `expectedMessageRevision` を照合する。
5. 改行を保持したまま前後の不要な空白だけを既存入力規則に合わせて正規化し、空文字と上限超過を拒否する。
6. `messageRevisions` へ before / after を追記し、`messages[].content` を最新版へ置換する。
7. message の `contentRevision` と session の `revision` を増やす。
8. 編集位置が要約境界へ与える影響を判定し、必要なら派生記憶を `pending` にする。
9. セッション JSON を1回だけ安全書き込みする。
10. ロック解放後、必要な再構築ジョブを開始する。

保存本文が現在の実効本文と同一なら `200` で現在値を返し、履歴も revision も増やさない。

`sourcePrefixFingerprint` は `summaryThroughMessageId` までの messageId と各
`contentRevision` を時系列でハッシュした値とする。要約境界より後だけを編集した場合は
fingerprint が変わらないため、session revision が増えても派生記憶は `fresh` のままでよい。
`pending / stale` または fingerprint 不一致の場合、prompt builder は conversationSummary、
relationshipState、sessionCanon を使用しない。

`promptBudgetReport` は元の生成時点の監査情報として保持する。本文依存の `generationWarnings` は旧本文の警告を残さず、手動本文を非破壊スキャンして更新する。警告があっても保存済み本文を自動リライトしない。

既存の要約確定処理 `mergeSummaryIfCursorUnchanged` はカーソル一致だけで結果を採用しているため、この機能と同時に `expectedSessionRevision` も照合するよう変更する。編集開始前の本文から作った要約が、編集後の同じカーソルへ合流することを防ぐ。

### 6.3 後続会話の扱い

過去発言を直しても、その後の発言は残す。たとえばユーザー発言を訂正した結果、直後のキャラクター応答と自然につながらなくなっても、ChapterFlow が暗黙に応答を削除・再生成することはない。

後続発言がある場合、保存確認に次を表示する。

> この発言より後の会話は残ります。訂正内容は次回以降の応答と記憶に反映されます。

後続削除や指定位置からの再生成は、将来の独立機能とする。

### 6.4 要約境界より新しい発言

編集対象が `summaryThroughMessageId` より後ろなら、既存の conversationSummary / relationshipState / sessionCanon にはまだ畳み込まれていない。

- 派生記憶の再構築は行わない。
- 次回プロンプトの recent messages が編集済み `content` をそのまま使うため、保存直後から反映される。
- セッション revision は増やし、進行中生成の古い応答コミットを防ぐ。

### 6.5 要約済み発言

編集対象が `summaryThroughMessageId` 以前なら、旧本文が conversationSummary、relationshipState、sessionCanon に含まれている可能性がある。この場合は全文履歴からセッション記憶を再構築する。

1. `derivedMemoryStatus = pending` を本文と同時に保存する。
2. 旧 conversationSummary、relationshipState、sessionCanon は保存上は残してもよいが、`pending / stale` 中はプロンプトに使用しない。
3. 実効本文の全メッセージを時系列の固定チャンクへ分け、空の派生状態から要約・関係性・セッション内潜在設定を再計算する。
4. 最後の短い recent messages は従来どおり要約せず残す。
5. ジョブ開始時の session revision と完了時の revision が一致する場合だけ結果を確定し、`fresh` にする。
6. 実行中に再編集・新規発言があれば結果を破棄し、最新 revision のジョブを再予約する。

再構築が完了するまでは、新規応答生成を無効にし「会話の記憶を再構築しています」と表示する。古い要約を使って即時生成するより、数秒待って訂正を確実に反映することを優先する。

失敗時は `stale` とし、会話閲覧と再編集は可能、新規応答生成は不可とする。「記憶を再構築」操作で再試行できる。

### 6.6 作品設定へ昇格済みの会話設定

セッション内潜在設定から作品設定へ昇格した項目は、ユーザーが明示的に採用した別の正本である。元発言の編集だけで自動削除しない。

編集対象の messageId が昇格根拠に含まれる場合、保存結果に `promotedCanonNeedsReview` の警告を含め、該当設定への導線を表示する。再構築後のセッション内項目は最新会話から作り直すが、作品設定側はユーザーが確認・修正する。

## 7. 小説本文編集

### 7.1 データモデルと保存場所

小説では、既存の generation log に `entryType: 'text-revision'` を追記し、`findGenerationRecords` が最新 `responseText` を重ねる方式を継続する。元の GenerationRecord を書き換えない。

既存の改訂行を後方互換で読めるようにしつつ、新規行へ次を追加する。

```ts
interface GenerationTextRevisionLogEntry {
  entryType: 'text-revision';
  generationId: string;
  responseText: string;
  revision: {
    revisionId: string;
    revisionNumber: number;
    source: 'manual-edit' | 'history-restore' | 'ng-auto-rewrite';
    before: string;
    after: string;
    beforeHash: string;
    afterHash: string;
  };
  updatedAt: string;
}
```

旧 `text-revision` 行に `revisionNumber` がない場合は、同 generationId のログ順から番号を導出する。新しい一覧取得処理は、GenerationRecord、最新本文、最新版番号を1回の後方走査で解決する。

生成時の request、reasoning、prompt snapshot は「その原文が生成された理由」の監査情報なので書き換えない。

### 7.2 draft 本文

draft 編集は次の順で行う。

1. プロジェクト書き込みロック内で generationId と `expectedRevisionNumber` を確認する。
2. `text-revision` を追記する。
3. generation markdown を実効本文で再生成する。
4. ReaderState へ最新版を返す。

採用済みのエピソード本文、StoryState、潜在設定、文脈要約には影響しない。

### 7.3 accepted 本文

accepted 編集では、`status = accepted` と `SceneRecord.acceptedGenerationId` を変更しない。

保存トランザクションでは先に表示上の正本を確定する。

1. project / generation / scene の対応と最新版番号を検証する。
2. `text-revision` を追記する。
3. generation markdown を更新する。
4. accepted generation 列から episode markdown を再構築する。
5. 同じ追記行に `derivationDirty` と owner token を記録する。
6. 編集した generation 以降の文脈要約を無効化する。
7. `storyStateRefresh` を `pending` にし、owner token を記録する。
8. ロック解放後に再抽出ジョブを開始する。

この時点で Reader は編集済み本文を表示し、採用ボタンは「採用済み」のままにする。再抽出は採用操作のやり直しではない。

### 7.4 accepted 本文列の再抽出

StoryState と潜在設定は、採用本文列から再生成可能な派生投影として扱う。古いシーンの訂正は後続シーンの解釈にも影響し得るため、編集対象だけへ差分パッチを重ねない。

再構築時間を抑えるため、次のチェックポイントを追加する。

```ts
interface AcceptedNarrativeCheckpoint {
  checkpointId: string;
  throughGenerationId: string | null;
  acceptedSequenceFingerprint: string;
  storyState: StoryState;
  latentCanonStore: LatentCanonStore;
  createdAt: string;
}
```

- `acceptedSequenceFingerprint` は、チェックポイントまでの generationId と各 text revision の順序付きハッシュである。
- episode 終端と一定シーン数ごとに作る。対応する prefix の fingerprint が一致するものだけを利用する。
- checkpoint 自体は派生キャッシュであり、削除されても先頭から再構築できる。
- `storyStateRefresh` には従来の generationId に加え、処理理由、起点 generationId、起点 text revision、accepted sequence fingerprint を保持する。旧形式は従来の1件抽出として解釈する。
- owner token は `generationId + textRevisionNumber + acceptedSequenceFingerprint` とする。ジョブ開始時、各モデル結果の適用直前、`fresh` 確定直前の3箇所で完全一致を確認する。

再抽出ジョブは次の順で行う。

1. エピソード・シーン順に accepted generation の実効本文列を取得する。
2. 編集対象より前の `fresh` な再構築チェックポイントがあれば利用する。なければ先頭から再構築する。
3. 編集対象以降の accepted derivation を `stale` にし、StoryState / latent canon の processedGenerationIds から外す。
4. チェックポイントの StoryState と潜在設定を作業用スナップショットへ読み込む。
5. 編集対象以降を時系列順に再抽出し、作業用スナップショットだけへ適用する。
6. 全件成功後、StoryState、潜在設定、derivation records、processedGenerationIds を同じ本文版の versioned bundle へ書く。
7. 文脈要約も編集対象以降を再構築する。
8. 開始時の accepted generation 列または text revision が変わっていれば、結果を確定せず最新版で再予約する。
9. bundle の全ファイルを安全書き込みした後、active bundle manifest を1回の安全置換で切り替える。

途中結果を現行 StoryState へ順次書き込まない。失敗時に「半分だけ新本文、半分は旧本文」の状態を作らないため、作業ファイルまたはメモリ上のスナップショットから最後に切り替える。

manifest 切替前に終了した bundle は未使用の作業データとして無視する。manifest 切替後は
StoryState、潜在設定、derivation records、processedGenerationIds の全読取が同じ bundleId を
経由する。起動時に manifest が指す bundle の完全性を検証し、壊れていれば直前 bundle へ
戻して `stale` にする。単なる複数ファイルの順次上書きは「一括確定」とみなさない。

現在の `beforeState` は古い差分ほど省略されるため、任意の過去シーン編集の唯一の復元手段には使わない。実装時に、一定間隔および各 episode 終端の再構築チェックポイントを追加する。チェックポイントがない旧プロジェクトは初回だけ先頭から再抽出する。

`authorUndecided` などユーザーが明示的に管理する項目、手動ロック、作品設定へ正式採用済みの項目は再抽出の初期条件として保持する。自動抽出部分だけを置き換える。

#### 7.4.1 StoryState の手動修正

現行の `PUT /story-state` は StoryState 全体を置き換えるため、どの値が自動抽出で、どの値がユーザー修正かを後から完全には判別できない。この区別を付けずに全再構築すると、ユーザー修正を失う危険がある。

accepted 過去本文編集を有効にする前提として、StoryState の手動保存時に「保存前の自動投影との差分」を追記する `StoryStateManualOverrideLog` を追加する。再構築では次の順で合成する。

1. accepted 本文から自動投影を再構築する。
2. `authorUndecided` と手動ロックを戻す。
3. 手動 override を保存順に再適用する。
4. 対象が消滅して適用できない override は無視せず `needsReview` として残す。

機能追加前の旧プロジェクトには override log がない。初回の全再構築前に現行 StoryState を `legacy-story-state-before-rebuild.json` へ退避し、再構築後との差分確認を必須にする。旧状態を自動投影として盲目的に重ねない。これにより、新本文の抽出結果を旧状態が上書きすることも、ユーザー修正を無告知で消すことも避ける。

`StoryStateManualOverrideLog`、legacy 退避、差分確認 API / UI は accepted 本文編集を有効化する
前提条件であり、後続 Phase へ分離しない。旧プロジェクトの初回再構築完了後は
`storyStateRefresh.status = awaiting-review` とし、旧状態と新しい自動投影の差分を表示する。
ユーザーが確認するまで生成・採用変更を禁止する。確認 API は「新しい投影を採用」と
「旧状態を手動 override として取り込む」を提供し、どちらも新しい override log として記録する。

### 7.5 再抽出中と失敗時

- `pending`: 本文閲覧・再編集・履歴閲覧は可能。新しい本文生成と採用変更は不可。
- `awaiting-review`: legacy 差分確認待ち。本文閲覧・再編集・履歴閲覧は可能。新しい本文生成と採用変更は不可。
- `fresh`: 最新本文版で派生投影が確定済み。通常操作へ戻る。
- `stale`: 本文と accepted は維持。新しい本文生成と採用変更は不可。「再抽出」から再試行できる。

Reader は `pending` 中に「採用本文を更新しました。設定を再抽出しています」と表示する。長時間化した場合だけ詳細と再試行を表示し、編集保存自体を失敗扱いにしない。

## 8. API 設計

### 8.1 ロールプレイ

```http
PATCH /api/projects/:projectId/roleplay/sessions/:sessionId/messages/:messageId
```

```json
{
  "content": "修正後の発言",
  "expectedSessionRevision": 12,
  "expectedMessageRevision": 1
}
```

成功時は通常の `RoleplaySessionView` と次を返す。

```json
{
  "session": {},
  "memoryRebuildStarted": true,
  "warnings": ["promoted_canon_needs_review"]
}
```

```http
GET /api/projects/:projectId/roleplay/sessions/:sessionId/messages/:messageId/revisions
POST /api/projects/:projectId/roleplay/sessions/:sessionId/messages/:messageId/revisions/:revisionId/restore
POST /api/projects/:projectId/roleplay/sessions/:sessionId/memory-rebuild
```

restore も `expectedSessionRevision` と `expectedMessageRevision` を要求する。

### 8.2 小説

```http
PATCH /api/projects/:projectId/generations/:generationId/text
```

```json
{
  "text": "修正後の本文",
  "expectedRevisionNumber": 2,
  "expectedStatus": "draft",
  "expectedAcceptedGenerationId": null
}
```

```http
GET /api/projects/:projectId/generations/:generationId/text-revisions
POST /api/projects/:projectId/generations/:generationId/text-revisions/:revisionId/restore
POST /api/projects/:projectId/story-state/reextract
GET /api/projects/:projectId/story-state/rebuild-review
POST /api/projects/:projectId/story-state/rebuild-review/resolve
```

小説本文の restore も `expectedRevisionNumber`、`expectedStatus`、
`expectedAcceptedGenerationId` を必須とする。旧 `text-revision` の `revisionId` は
`legacy:` + generationId + ログ行 byte offset + afterHash から決定論的に生成し、ログ末尾へ
追記しても同じ ID を返す。

成功応答には `generationId`、実効本文、本文 revision、status、`derivationStatus` を含める。accepted の場合も status は `accepted` のままである。

### 8.3 エラー

- `400`: 空文字、長さ上限、壊れた revisionId
- `404`: project / session / message / generation が存在しない
- `409`: expected revision 不一致、生成・採用変更・再抽出との競合
- `422`: 対象の状態では編集不可（archived session など）
- `503`: 保存先へ安全に書き込めない

`409` は最新の revision 番号だけを返し、クライアントは自動上書きしない。最新本文を再取得し、ユーザーに再編集を促す。

本文 revision が一致していても、`expectedStatus` または
`expectedAcceptedGenerationId` が現在値と異なる場合は `409` とする。draft 編集確認を見た
ユーザーの保存が、別タブの採用操作によって暗黙に accepted 編集へ変わることを許可しない。

## 9. UI 設計

### 9.1 ロールプレイ

- 各ユーザー・キャラクター吹き出しのメニューに「編集」を追加する。
- 編集中は同じ位置を複数行 textarea にし、「保存」「キャンセル」を表示する。
- 通常表示は最新版だけとし、旧本文を折り畳み表示しない。
- 改訂済み発言には控えめな「編集済み」表示を付ける。本文内容の邪魔にならない位置に置く。
- 「編集済み」またはメニューの「編集履歴」から、日時と版を一覧表示する。
- 後続会話がある発言では保存前に確認する。
- 要約済み発言の保存後は、再構築完了まで送信欄を無効にする。

### 9.2 小説 Reader

- generation 操作群に「本文を編集」を追加する。
- 編集画面は Markdown の生テキストを扱う複数行 textarea とする。
- draft は通常確認だけ、accepted は「採用状態を維持したまま、設定と記憶を再抽出します」と明示して保存する。
- 過去の accepted シーンでは、再抽出対象となるシーン数を確認画面に示す。現在の末尾シーンなら通常は1件、古いシーンほど後続分を含むため API 利用量が増えることも明記する。
- 保存直後に編集済み本文へ切り替え、accepted 表示を維持する。
- 再抽出状態を既存の storyStateRefresh 表示へ統合する。
- 履歴は Reader のメニューから開き、選択版をプレビューしてから復元する。
- 契約・NG候補は保存を妨げず、保存後の警告欄に表示する。

## 10. 排他・原子性・復旧

### 10.1 排他

- ロールプレイは session lock、小説は project data lock と既存の refine / story-state guard を使う。
- 編集開始後に別操作が本文を変えた場合、保存は `409` とし自動マージしない。
- 生成開始時には最新 revision をスナップショットし、完了時に一致しなければ旧文脈の生成結果を自動コミットしない。

### 10.2 書き込み順

- ロールプレイは最新版、履歴、派生状態を同じ session JSON の安全置換で確定する。
- 小説は追記ログを正本とし、generation markdown と episode markdown は再構築可能な派生ファイルとする。
- accepted 本文の `text-revision` 行は本文と同時に `derivationDirty` owner token を記録する。state.json の `pending` 保存前に終了しても、ReaderState・生成・採用操作の入口でログと active bundle fingerprint を照合し、dirty を検出したら `pending` を復元してから操作を拒否する。
- 小説でログ追記後に markdown 更新が失敗した場合、次回読み込み時に実効本文から markdown を修復する。ログを巻き戻さない。
- 再抽出結果は作業スナップショット完成後に切り替え、部分適用を避ける。

### 10.3 再起動復旧

起動時または ReaderState / session 読み込み時に `pending` を検査する。

- 対応するプロセス内ジョブがなければ再予約する。
- 本文版が変わっていれば古いジョブ情報を破棄し、最新版で再予約する。
- 同一入力で繰り返し失敗した場合は `stale` にし、無限再試行しない。

連続編集で古い再抽出へモデル費用を使い続けないよう、ジョブ開始前に短い debounce を置き、未開始ジョブは最新版へまとめる。開始済みジョブの結果も fingerprint 不一致なら適用せず、次の最新版ジョブへ引き継ぐ。

## 11. 後方互換と移行

- `RoleplayMessage.contentRevision` 欠損は 0、`messageRevisions` 欠損は空配列、`derivedMemoryStatus` 欠損は現在の要約カーソルと矛盾がなければ `fresh` と解釈する。
- `RoleplaySession.schemaVersion` は optional 追加だけなら 1 のままとし、読めない構造変更が必要になった場合だけ 2 へ上げる。
- 既存 generation log の `text-revision` は引き続き読める。新フィールド欠損を理由に破損行扱いしない。
- 既存の generation markdown / episode markdown は、本文編集時または修復処理時に最新版へ再生成する。
- 初回の古い accepted 本文編集でチェックポイントがない場合、先頭からの再抽出になることを UI に表示する。

## 13. テスト計画

### 13.1 単体テスト

- 原文、複数改訂、復元後の実効本文解決
- 同一本文保存が no-op になること
- 旧 `text-revision` 行と新形式の混在
- expected revision 不一致
- 要約カーソル前後の影響判定
- accepted の status / acceptedGenerationId が変化しないこと
- 編集対象以降だけを再抽出対象にする順序計算
- ジョブ完了時の本文版不一致で結果を破棄すること
- 要約境界より後のロールプレイ編集では prefix fingerprint が変わらず `fresh` を維持すること
- 旧 text-revision の synthetic revisionId が追記後も変わらないこと

### 13.2 サービス統合テスト

- user 過去発言を編集し、後続会話が残る
- character 過去発言を編集し、次回プロンプトが最新版を使う
- 要約済み発言編集で旧要約を使わず、再構築後に送信可能になる
- draft 編集で generation markdown が更新される
- accepted 編集で採用維持、episode markdown 更新、再抽出 pending になる
- 再抽出失敗でも本文と accepted が維持され、stale になる
- 復元が新しい履歴として残る
- archived session 編集が拒否される

### 13.3 E2E

- ロールプレイのユーザー吹き出しを編集し、再読込後も最新版だけが表示される
- 編集履歴から初版を復元し、再読込後も復元版が表示される
- accepted 本文を編集し、採用表示を保ったまま再抽出表示が pending → fresh になる
- 再抽出エラー時に再試行できる
- 別タブ編集競合で意図しない上書きが起きない
- draft 編集中に別タブで採用された場合、本文 revision が同じでも 409 になる
- 小説 restore 中の別タブ編集が expected revision で 409 になる

### 13.4 性能・耐久

- 500メッセージ、各メッセージ10改訂のセッション読込時間とファイルサイズ
- 100シーンの先頭付近を編集した全再抽出のモデル呼び出し数と復旧時間
- 再抽出中のアプリ終了・再起動
- text-revision 追記後かつ state pending 保存前の強制終了から dirty を復元する
- versioned bundle 完成前・manifest 切替直前・切替直後の各強制終了で旧版または新版の一組だけを読む
- generation log 末尾に破損行がある場合の最新版解決

### 13.5 操作ガード

- `pending / stale / awaiting-review` 中は通常生成、stream 生成、accept、unaccept、採用差し替えをサーバーが拒否する
- UI の disabled だけに依存せず、各サービスが project lock 取得後に状態を再検査する
- NG リライトを含む全本文変更が共通 revision service を通り、ログ正本を markdown より先に確定する

## 14. 受け入れ条件

1. ユーザー・キャラクター双方の過去発言を編集できる。
2. 通常画面には実効本文だけが表示され、旧版は履歴を開いた場合だけ見える。
3. 過去発言編集で後続会話は消えない。
4. 次回生成は編集済み発言を使い、旧要約が混入しない。
5. draft / accepted の本文を手入力で編集できる。
6. accepted 本文編集後も status と acceptedGenerationId が維持される。
7. accepted 本文編集後、StoryState・潜在設定・文脈要約が編集済み本文から再抽出される。
8. 再抽出失敗でも編集本文と採用状態を失わない。
9. 履歴からの復元ができ、復元操作そのものも履歴へ残る。
10. 同時更新で無言の上書きが起きない。

## 15. 実装時に固定して確認する事項

本設計は機能方針を確定しているが、実装前に次の数値だけは既存制限と実測に合わせて決める。

- ロールプレイ発言と小説本文の最大文字数
- 再構築チャンクのメッセージ数・文字数
- accepted rebuild checkpoint の間隔
- `pending` を長時間扱いへ切り替える秒数
- 自動再試行回数

これらは挙動の意味を変えない運用値であり、「双方の発言を編集可能」「採用維持」「最新版のみ通常表示」「派生データ再抽出」という決定事項は変更しない。
