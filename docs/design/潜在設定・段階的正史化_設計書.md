# 潜在設定・段階的正史化 設計書

作成日: 2026-08-06
最終更新日: 2026-08-06（設計レビュー A1〜C6 反映）
対象バージョン: 未定（0.1.0-beta.11 以降を想定）
実装後の扱い: 実装完了後 `archive/` へ移動する。

## 0. 結論

本改修では、作品開始前に人間が詳細設定を完成させる方式から、次の方式へ移行する。

> 人間は、作品に求める少数の約束と禁止事項を決める。
> アプリは、その約束を守るために必要な設定だけを補完する。
> 補完した設定は本文に現れるまで暫定とし、採用済み本文で明らかになった内容だけを正史にする。

本設計の中心は「設定項目を減らす」ことではない。次の3つを別の責務として扱うことで、開始の速さと整合性を両立する。

1. **創作契約**: ユーザーが明示した、作品が守るべき約束・禁止事項・好み。
2. **潜在設定**: アプリが補完した、未公開かつ変更可能な設定。
3. **公開済み正史**: 採用済み本文または確定した会話で、実際に提示された事実・主張・認識。

重要な原則は以下とする。

- アプリが推測した内容を `hard` な創作契約へ昇格しない。
- 開始時に巨大な裏設定を作らない。薄い初期補完と進行中の追加補完を組み合わせる。
- 潜在設定は本文に出るまで自由に差し替えられる。
- 小説のドラフト本文は正史化の根拠にしない。採用操作を境界にする。
- 台詞、噂、思い込みを客観的事実として正史化しない。
- ロールプレイ中に生まれた事実は、原則としてセッション内だけで正史化する。
- 既存の正史や創作契約との衝突を、アプリが無言で上書きしない。
- 作者はいつでも潜在設定を閲覧・編集できるが、既定ではネタバレを隠す。

### 0.1 優先度

| 優先度 | 改修 |
|---|---|
| P0 | 創作契約の保存・編集・生成プロンプト最優先注入 |
| P0 | 潜在設定ストア、公開状態、根拠、競合優先順位 |
| P0 | 小説の採用を境界にした段階的正史化と採用取消時の巻き戻し |
| P1 | 一文から開始できるクイックセットアップと薄い初期補完 |
| P1 | ネタバレを隠す作品設定UI、潜在設定の閲覧・編集・ロック |
| P1 | semantic hard contract の生成後検証と最大1回の修復 |
| P1 | 進行に応じた潜在設定の追加・整理 |
| P2 | ロールプレイのセッションローカル正史と作品への明示昇格 |
| P2 | 余韻カード、物語コンパスなどインタラクティブUIへの利用 |

## 1. 背景

### 1.1 現在の落とし穴

現行の設定相談は、作品の核、確認済み事項、候補、未決定事項、人物、関係性、世界観、文体、NG、冒頭候補などを丁寧に組み立てられる。一方、丁寧に設定するほど次の問題が大きくなる。

- 開始までの時間が長くなる。
- ユーザーは本文より先に設定表を読み、作品の驚きを失う。
- 重要度の違う設定が同じ層へ並び、モデルが何を最優先すべきか判断しにくい。
- 細部を一箇所でも破ると、作品全体への信頼が急激に失われる。
- 人間が先に決めすぎることで、進行中に自然に生まれる発見や意外性が減る。
- 設定を守らせるためにプロンプトが長くなり、かえって重要な条件が薄まる。

特に、「瞳の色」と「この人物は最後まで裏切らない」が同じ設定一覧に置かれると、作品の根幹と装飾的な事実の区別がつかない。本改修では、前者を正史または潜在設定、後者を創作契約として別管理する。

### 1.2 既存実装との接続

既存機構には、本設計の土台がすでにある。

| 新しい役割 | 再利用する既存機構 |
|---|---|
| 人間が明言したこと | `SetupDraft.confirmed`、`coreConcept`、`ng`、手動ロック |
| アプリの候補 | `SetupDraft.candidates` |
| まだ決めないこと | `SetupDraft.undecided`、`StoryState.authorUndecided` |
| 人物の見せない面 | `Character.secrets` |
| 進行中の正史 | `StoryState` の人物状態・イベント・伏線・情報範囲 |
| 本文からの抽出 | `storyStateService.updateStoryStateFromAcceptedScene` |
| 矛盾の走査 | `refineScanService` と生成後設定レビュー |
| ロールプレイの固定文脈 | `RoleplayContextSnapshot` |
| ロールプレイの派生状態 | `conversationSummary`、`relationshipState` |

ただし、現行データには「アプリが補完した暫定設定」と「本文で確定した正史」の共通ライフサイクルがない。`Character.secrets` は非表示情報だが、暫定か確定か、どの本文が根拠かを持たない。本設計ではその不足だけを新しいストアで補う。

## 2. 目的と非目標

### 2.1 目的

- 一文程度の希望から、詳細設定を入力せず作品を開始できる。
- ユーザーが求める要素を少数の創作契約として強く守る。
- アプリが補完した設定を、本文に出るまで変更可能に保つ。
- 設定の説明ではなく、本文の進行を通して世界や人物が明らかになる体験を作る。
- 作者がネタバレを避けたい場合、潜在設定の本文を通常UIと通常APIレスポンスへ出さない。
- 作者が監督として管理したい場合、潜在設定を閲覧・編集・ロックできる。
- 採用取消、本文の差し替え、ロールプレイ再生成でも、根拠を失った正史を追跡できる。
- 既存プロジェクトと既存ロールプレイセッションをそのまま読み込める。
- 補完・検証の追加APIコストと待ち時間に上限を設ける。

### 2.2 非目標

- AIが作品の重要な方向性を作者に代わって決定すること。
- 開始時に世界設定集、人物事典、全プロットを完成させること。
- 潜在設定どおりの伏線回収を強制すること。
- すべての本文記述について客観的真偽を完全自動判定すること。
- 採用済み本文を設定変更に合わせて無断で書き換えること。
- 既存の `world.md`、`characters.json`、`story-state.json` を直ちに新形式へ全面移行すること。
- ロールプレイで生まれた設定を自動的に別セッションや小説の正史へ持ち込むこと。
- 潜在設定をLLM事業者から秘匿すること。生成に必要な項目は従来の作品設定と同様に外部APIへ送信される。

## 3. 用語と状態

### 3.1 創作契約

`CreativeContract` は、ユーザーが作品に対して明示した条件である。

| 種別 | 例 | 強度 |
|---|---|---|
| `promise` | 二人の信頼が時間をかけて育つ | hard |
| `prohibition` | 護衛は主人公を裏切らない | hard |
| `preference` | 冷たく静かな雰囲気 | soft |

- `hard` はユーザーの明示操作だけで作成する。
- AIが会話から推測した好みは `soft` 候補にできるが、ユーザー確認なしに `hard` へしない。
- hard項目は合計8件を上限とし、UIでは3〜5件を推奨する。
- soft項目は12件を上限とする。
- 文言単位の禁止は既存のNG表現機能を正本とし、創作契約へ重複保存しない。
- hard項目同士のsemantic conflictはLLM判定に偽陽性があり得るため、確認なしの保存拒否にはしない。初回`PUT`は409と競合候補・`conflictFingerprint`を返し、作者が内容を確認したうえで、同じrevisionと`confirmConflictFingerprint`を付けて再`PUT`した場合だけ保存を許可する。作成順・配列順で自動決定しない。

### 3.2 潜在設定

`LatentCanonItem` は、本文で利用できるが、まだ正史ではない補助設定である。

ライフサイクルは次のとおり。

```text
provisional ──採用本文で曖昧に示唆──> foreshadowed
     │                                  │
     ├──採用本文で明示──────────────────> revealed
     │                                  │
     ├──不要・競合──────────────────────> retired
     │                                  │
     └──作者が明示確定──────────────────> revealed
```

- `provisional`: アプリが補完しただけ。自由に差し替え可能。
- `foreshadowed`: 採用済み本文に曖昧な示唆がある。使用義務はなく、真相はまだ変更可能。
- `revealed`: 採用済み本文または作者操作に明示的な根拠がある。
- `retired`: 採用されなかった、不要になった、または別の正史と競合して退役した。

`foreshadowed` は「いつか必ず回収する約束」ではない。生成プロンプトでは低優先の可能性として扱い、作者がロックしない限り強制的に再利用しない。

図は通常の前進遷移だけを示す。採用取消、根拠メッセージの置換、evidence削除では、`revealed` / `foreshadowed` から残存evidenceまたは`baseStatusWithoutEvidence`へ降格する逆遷移がある。状態を単純に一方向のenumとして実装しない。

### 3.3 公開状態と真偽を分離する

「読者へ見えたか」と「客観的に真実か」は別軸である。

`epistemicStatus` は次の値を取る。

- `fact`: 作品世界の事実として扱える。
- `claim`: 人物がそう主張したことは正史だが、内容の真偽は未確定。
- `belief`: 人物がそう信じていることは正史だが、内容の真偽は未確定。
- `rumor`: 噂として存在することだけが正史。
- `unknown`: 真偽分類ができない。自動で `fact` に上げない。

台詞中の「私は王の娘だ」は原則 `claim` とする。「王の娘であることが地の文と証拠で明示された」場合にだけ、別の `fact` または既存項目の `fact` 化を検討する。

### 3.4 3種類の可視性を混同しない

1. **作者UIでの可視性**: ネタバレ防止のため隠すか。
2. **読者への開示状態**: 本文中で未公開、示唆、明示のどこか。
3. **登場人物の認識範囲**: 誰が知っているか。

作者UIの表示設定は `ProjectState.uiState`、本文上の開示状態は `LatentCanonItem.status`、人物の認識範囲は既存の `knownBy` / `explicitlyUnknownBy` と新規項目の同名フィールドで管理する。

## 4. UX設計

### 4.1 クイックセットアップ

新規作品は、最短で一つの自由記述だけから開始できる。

```text
人を信じられない魔女と寡黙な護衛が、雨の夜に逃げる話。
時間をかけて信頼が育ってほしい。護衛は最後まで裏切らない。
```

クイックセットアップ画面は、次の3領域だけを主表示する。

1. **見たい作品・関係・感情** — 自由記述。唯一の必須入力。
2. **絶対に守ってほしいこと** — 任意。hard promise / prohibition候補。
3. **最初に見たい場面** — 任意。小説では最初の希望、ロールプレイでは会話舞台。

詳細な人物、世界、口調、過去、秘密、関係性は「詳細を自分で決める」に退避する。既存の設定相談は廃止せず、監督型の入口として残す。

クイックセットアップは`createProject`への別ルートではなく、既存setup sessionの短縮モードとして実装する。`SetupSession`に`setupMode?: 'quick' | 'full'`を追加し、欠損は`full`と解釈する。「詳細を自分で決める」は同じsessionを`full`へ切り替え、会話・draft・lockを維持する。クイック入力から作った契約候補、最低限の人物、潜在設定も`SetupDraft` / `SetupCommitPlan`を通して確認・commitする。

開始操作では次を行う。

1. 入力から創作契約候補を抽出する。
2. hard候補だけを短い確認カードで見せる。
3. 確認後、同じsetup draft上で物語開始に必要な最小人物・舞台と、最大8件の薄い潜在設定を生成する。
4. 潜在設定生成だけが失敗した小説は、空latent storeと`latentSeedStatus: 'failed'`をcommit planへ入れる。
5. `setupSessionService.commitSetupSession`から`createProject`を呼び、project/world/characters/storyState/creative contract/latent canon/accepted derivationsを同一作成列で保存する。
6. 保存成功後、潜在設定の本文は表示せず件数だけを知らせ、小説では最初の生成画面、ロールプレイでは最初の会話へ遷移する。

補完が失敗しても、ユーザー入力だけで安全に開始できる場合は作品作成を失敗扱いにしない。小説では、創作契約と`coreConcept`の作成に成功し、潜在設定生成だけが失敗した場合、commit planへ空のlatent storeと`latentSeedStatus: 'failed'`を入れて続行できる。作品設定には「未公開設定を準備できませんでした。物語の進行中に補完します」と表示する。ロールプレイは会話相手となる最小Characterを必要とするため、その生成にも失敗した場合はcommitせず再試行を案内する。

### 4.2 作品設定画面

作品設定の先頭に、次の順でカードを置く。

1. **作品の約束** — 常に内容を表示。編集・並べ替え・無効化が可能。
2. **公開済みの設定** — 本文ですでに明らかになった内容。
3. **未公開設定** — 既定では「人物3件・世界2件・関係1件」のような件数だけ表示。
4. **まだ決めないこと** — 既定では件数だけ表示。作者が開けば内容を確認可能。

未公開設定を開く操作には「先の展開に関する内容が含まれます」を表示する。プロジェクト単位の表示モードは次の2つとする。

- `shielded`（既定）: 内容を通常レスポンスと通常UIへ出さない。
- `visible`: 内容を設定画面へ表示する。

ローカルアプリであるため、これはアクセス制御ではなくネタバレ防止UXである。ただし `shielded` の通常APIは潜在設定本文を返さず、誤表示を構造的に防ぐ。

### 4.3 潜在設定の編集

- 内容を編集するには、作者が明示的に未公開設定を開く。
- 手動編集した項目は `manualLock = true` にする。
- manual lockは作者の明示操作でのみ解除できる。自動整理・自動補完は解除しない。
- `provisional` は確認なしで編集・退役できる。
- `foreshadowed` の変更時は、示唆された場面を表示して確認する。
- `revealed` の変更は「正史の変更」として扱い、影響する採用本文と設定を提示する。
- 正史変更に合わせて採用本文を自動書き換えない。必要なら別途書き直し案を作る。

### 4.4 生成中の表示

hard契約に意味検証が必要な項目がある場合も、生成本文のchunkはSSEへ即時転送し、作者が読み始められるようにする。`strict` は既定のまま、表示中の本文を暫定稿として扱い、検証・修復後の本文が変わった場合は `replace` eventで確定本文へ全文差し替えする。`done.record`と再読込後のGETを最終正とする。

- `strict`: 暫定本文をストリーミング表示しながら厳格に検証する。本文生成に加え、検証、最大1回の修復、再検証の最大3回の追加モデル呼び出しがある。
- `fast`: ストリーミングを優先し、完了後に検証・修復する。暫定本文に違反が見える可能性を明示する。

この選択は作品単位で保存する。生成前と生成中のUIには「作品の約束を確認します（追加1〜3回のAPI呼び出し）」と、`生成中 → 約束を確認中 → 修復中 → 再確認中`の現在phaseを表示する。固定秒数はprovider・model差が大きいため約束せず、将来telemetryから同一modelの実績中央値を出せる場合だけ時間目安を表示する。

## 5. データ設計

### 5.1 保存ファイル

既存の `project.json` へ未公開本文を混在させず、次のファイルを追加する。

```text
data/projects/{projectId}/creative-contract.json
data/projects/{projectId}/latent-canon.json
data/projects/{projectId}/accepted-derivations.json
```

`creative-contract.json` はユーザーが指定した条件、`latent-canon.json` はアプリ補完・公開根拠・未解決競合の台帳を持つ。`accepted-derivations.json` は採用本文1件に対して1回だけ行うStoryState/canon共通抽出の構造化結果と適用状況をキャッシュする。既存の `world.md`、`characters.json`、`story-state.json` は役割を維持する。

### 5.2 創作契約型

```ts
export type CreativeContractKind = 'promise' | 'prohibition' | 'preference';
export type CreativeContractStrength = 'hard' | 'soft';

export interface CreativeContractItem {
  contractId: string;
  kind: CreativeContractKind;
  strength: CreativeContractStrength;
  text: string;
  source: 'user' | 'manual' | 'ai-suggested';
  status: 'active' | 'disabled';
  createdAt: string;
  updatedAt: string;
}

export interface ContractException {
  exceptionId: string;
  contractId: string;
  generationId: GenerationId;
  evidenceExcerpt: string;
  reason?: string;
  createdAt: string;
}

export interface CreativeContract {
  schemaVersion: 1;
  projectId: ProjectId;
  revision: number;
  items: CreativeContractItem[];
  exceptions: ContractException[];
  verificationMode: 'strict' | 'fast';
  updatedAt: string;
}
```

正規化規則:

- `ai-suggested` は `soft` のみ許可する。
- `promise` / `prohibition` は原則 `hard`、`preference` は `soft` とする。
- hardは合計8件、softは12件を超えた入力を400で拒否する。
- 1件は500文字以内、空文字と重複を拒否する。
- semantic conflict検査でhard同士の衝突候補があれば409、競合候補、`conflictFingerprint`を返す。同じrevisionとfingerprintを付けた明示確認付き再PUTは保存を許可する。
- 既存NG表現の文言をそのまま契約へ複製しない。
- `exceptions`欠損は空配列へ正規化する。exceptionは同じprojectのactive/disabled contractIdとaccepted generationIdだけを参照でき、evidenceExcerptは160文字以内とする。
- exceptionは契約を無効化しない。契約を削除する場合も監査履歴として残すが、以後の検証対象からは外す。

### 5.3 潜在設定型

```ts
export type CanonLifecycle = 'provisional' | 'foreshadowed' | 'revealed' | 'retired';
export type CanonEpistemicStatus = 'fact' | 'claim' | 'belief' | 'rumor' | 'unknown';
export type CanonScope = 'world' | 'character' | 'relationship' | 'history' | 'plot' | 'other';

export interface CanonEvidence {
  kind: 'generation' | 'roleplay-message' | 'roleplay-promotion' | 'manual';
  disclosure: 'foreshadowed' | 'revealed';
  generationId?: GenerationId;
  sceneId?: SceneId;
  sessionId?: RoleplaySessionId;
  messageId?: string;
  excerpt?: string;
  createdAt: string;
}

export interface LatentCanonItem {
  canonId: string;
  scope: CanonScope;
  subjectCharacterIds?: CharacterId[];
  statement: string;
  status: CanonLifecycle;
  baseStatusWithoutEvidence: 'provisional' | 'retired';
  statusBeforeRetired?: Exclude<CanonLifecycle, 'retired'>;
  epistemicStatus: CanonEpistemicStatus;
  knownBy?: CharacterId[];
  explicitlyUnknownBy?: CharacterId[];
  source: 'setup' | 'on-demand' | 'generation' | 'roleplay' | 'manual';
  manualLock: boolean;
  evidence: CanonEvidence[];
  supersedesCanonId?: string;
  retiredReason?: 'unused' | 'contradicted' | 'replaced' | 'evidence-removed' | 'manual';
  createdAt: string;
  updatedAt: string;
}

export interface CanonConflict {
  conflictId: string;
  generationId: GenerationId;
  canonId?: string;
  contractId?: string;
  kind: 'revealed-canon' | 'hard-contract';
  summary: string;
  evidenceExcerpt: string;
  status: 'pending' | 'resolved' | 'exception-accepted' | 'dismissed';
  createdAt: string;
  resolvedAt?: string;
}

export interface LatentCanonStore {
  schemaVersion: 1;
  projectId: ProjectId;
  revision: number;
  items: LatentCanonItem[];
  processedGenerationIds: GenerationId[];
  pendingConflicts: CanonConflict[];
  updatedAt: string;
}

export interface NarrativeObservation {
  observationId: string;
  kind: 'situation' | 'character-state' | 'event' | 'thread' | 'canon';
  operation: 'add' | 'update' | 'resolve';
  targetId?: string;
  text: string;
  epistemicStatus: CanonEpistemicStatus;
  disclosure: 'foreshadowed' | 'revealed';
  subjectCharacterIds?: CharacterId[];
  actorCharacterId?: CharacterId;
  recipientCharacterId?: CharacterId;
  knownBy?: CharacterId[];
  explicitlyUnknownBy?: CharacterId[];
  evidenceExcerpt: string;
}

export interface AcceptedNarrativeDerivation {
  generationId: GenerationId;
  extractedAt: string;
  observations: NarrativeObservation[];
  // 以下2つは正規化済みobservationsからserverが作る再試行用cache。LLM出力ではない。
  storyStatePatch: unknown;
  canonPatch: unknown;
  status: 'extracted' | 'partially-applied' | 'applied' | 'stale';
  storyStateAppliedAt?: string;
  canonAppliedAt?: string;
  lastError?: string;
}
```

制約:

- `statement` は1件2,000文字以内とする。
- 自動生成時は1回最大8件、activeな `provisional` / `foreshadowed` は合計40件を上限とする。
- 上限超過時は、未使用・未ロック・低関連の `provisional` から `retired` にする。削除はしない。
- `revealed` とmanual lock項目は自動退役しない。
- `revealed` は必ず1件以上のevidenceまたは `source = manual` を持つ。
- `fact` への自動昇格は、台詞や人物の内心だけを根拠にしない。
- evidenceのexcerptは監査用の短い抜粋に限定し、本文全体を複製しない。
- `baseStatusWithoutEvidence`はevidenceをすべて除いた場合の復元先である。setup/on-demand由来の潜在設定は`provisional`、採用本文・roleplayから新規抽出された項目は`retired`とする。既存データ欠損時はsourceから補正する。
- evidence削除時は、残ったevidenceの`disclosure`から`revealed`優先、次に`foreshadowed`を再計算し、根拠が無ければ`baseStatusWithoutEvidence`へ戻す。`provisional → foreshadowed → revealed`の途中状態を一つのprior fieldで復元しない。
- `statusBeforeRetired`は手動退役・競合退役を取り消す場合だけ使い、evidence喪失時の復元先には使わない。
- `processedGenerationIds`はStoryStateの同名集合と独立に持ち、canon patchの二重適用を防ぐ。
- `pendingConflicts`は本文や潜在設定の全文を複製せず、作者が判断できる短いsummaryとevidence excerptだけを持つ。
- `accepted-derivations.json`はgenerationIdを一意キーとし、同じgenerationに対して複数レコードを作らない。抽出成功・保存部分失敗時の再試行は、モデルを再呼び出しせずキャッシュ済みpatchを使う。

`RoleplayContextSnapshot` に、セッション開始時点の創作契約と関連潜在設定を非公開スナップショットとして保持する。

## 6. 状態遷移と正史化

### 6.1 小説生成前

生成プロンプトの優先順位を次とする。

1. アプリ固定の不変契約
2. activeなhard creative contract
3. manual lockされた設定
4. revealed canon
5. 現在の `StoryState`
6. 今回の場面に関連する `foreshadowed` / `provisional`
7. soft preference
8. その他の参考資料

hard契約は`promptBuilder`のrequired section `user.creativeContractHard`として追加し、プロンプト予算で省略・切り詰めない。定数は次を初期値とする。

| 定数 | 値 | 用途 |
|---|---:|---|
| `CREATIVE_CONTRACT_HARD_MAX_CHARS` | 4,000 | hard項目本文と項目区切りの集約上限 |
| `CREATIVE_CONTRACT_HARD_SECTION_RESERVE` | 4,512 | 見出し・引用タグ・省略不能本文の最低予約 |
| `LATENT_CANON_SELECTED_MAX_ITEMS` | 12 | 1回の生成・抽出へ渡す関連canon上限 |

hard 8件の件数上限に加え、render後4,000字の集約上限も保存時に検査する。required sectionが既存のprompt総予算に収まらない場合は、`promptBudget.ts`のrequired overflow判定を通して既存の`prompt_budget_exceeded`を返し、モデルを呼ばない。hard契約専用の別エラー経路は作らない。

soft契約は保存上はcreative contractに置くが、プロンプト上は既存の`Memory.type === 'preference'`と同じpreferences経路へ合流させる。`contractId`と正規化本文で重複を除き、二つの好みセクションを作らない。softは既存のoptional縮小順に従う。

`ContractException`は過去の採用済みgenerationにだけ作用する。該当generation由来のrevealed canonをプロンプトへ入れる場合は「この事実はcontractIdに対する作者承認済みの例外」と明示し、hard契約とcleanな正史が無説明で衝突する状態を避ける。新しい本文の検証ではhard契約を引き続き有効にし、exceptionを将来の追加違反へ一般化しない。

潜在設定は全件注入しない。今回の希望、視点人物、現在の伏線、直近本文に関係する最大12件だけを選ぶ。選ばれなかった潜在設定は、存在しないものとして自由に生成してよい。ただし新しい記述がrevealed canonと矛盾してはならない。canon抽出で既存`canonId`を照合するときも、全40件ではなく同じ関連選択を通した候補だけをモデルへ渡し、照合不能な新事実は新規項目として返させる。

LLMへ渡すsemantic照合候補は最大12件に制限するが、新規canon patchの適用前にはserver側で全active canonを対象に決定的重複検査を行う。`scope`と`subjectCharacterIds`が一致し、`normalizedStatement`が同一、または一方が他方を明確に包含する場合は新規作成せず既存`canonId`へのmerge候補にする。決定的に判断できないsemantic重複は無理にmergeせず`pendingConflicts`へ送る。プロンプト予算削減のためにcanon台帳を重複分裂させない。

### 6.2 生成後の契約検証

検証は次の順で行う。

1. 既存のNG表現・明示語句を決定的に検査する。
2. hard creative contractへの意味上の違反を、契約IDごとの `pass` / `fail` / `uncertain` で検査する。
3. revealed canonとの明確な矛盾を検査する。
4. `fail` がある場合、違反箇所と周辺だけを対象に最大1回修復する。
5. 修復後に再検査する。

修復後も `fail` または `uncertain` が残る場合:

- 本文を自動採用しない。
- `strict` では暫定本文を表示しながら検証し、検証完了時に「作品の約束を確認できませんでした」を表示して、再生成・問題箇所を確認・そのまま表示を選ばせる。
- `fast` ではドラフトへ警告を付け、採用時に明示確認する。
- 無制限に修復を繰り返さない。
- 警告を無視して採用した場合も、創作契約自体を自動変更しない。

検証モデルには、契約、必要な正史、生成本文だけを渡す。未関連の潜在設定は渡さない。検証結果と修復回数はgeneration telemetryへ残すが、未公開設定本文を診断DTOへ複製しない。

モデルとtimeoutは次に固定する。

- semantic verifier / 再検証: 作品のactive provider・active model、各30秒。
- 局所修復: 作品のactive provider・active model、既存本文生成と同じ120秒。
- verifier timeout / parse失敗: `uncertain`として扱い、別modelへ自動フォールバックしない。

処理順は次とし、既存の生成後自動設定レビューと並行させない。

1. 本文を生成し、server bufferへ保持しながらclientへ暫定chunkを転送する。
2. 契約検証、必要なら最大1回の局所修復、再検証を完了する。
3. 最終本文または`contractReviewRequired`付きの警告ドラフトを`GenerationRecord`として保存する。
4. 最終的に保存されたdraftを対象に、`reservePostGenerationMaintenanceForDraftUnlocked`で既存refine maintenanceを予約する。
5. `ProjectState`を保存し、その後は既存の`maintenanceBlocksGeneration`に従う。

したがって、契約検証中にrefine automationは開始・予約されない。契約検証は現在の生成requestとproject generation lockの内側で同期実行されるため、`ProjectState.refineMaintenance`へ新phaseは作らない。検証失敗・timeoutでも作者確認用draftを保存した場合は、その保存後にだけmaintenanceを予約する。本文を破棄してgeneration recordを作らない場合は予約しない。

### 6.3 採用による昇格

小説では、`GenerationRecord.status === 'accepted'` になった後の抽出だけが状態遷移を行える。

1. 採用本文から、事実・主張・信念・噂・示唆を抽出する。
2. 既存の `canonId` と対応するものは、そのIDを維持して状態とevidenceを更新する。
3. 明示された潜在設定は `revealed` へ移す。
4. 曖昧に示唆されただけなら `foreshadowed` にする。
5. 潜在設定に無かった新事実は、新しい `revealed` 項目として追加できる。
6. 台詞・噂・内心は `claim` / `rumor` / `belief` とし、客観的内容を `fact` にしない。
7. 既存の潜在設定と採用本文が衝突した場合、採用本文を優先し、潜在設定を `retired: contradicted` にする。
8. revealed canonまたはhard契約と衝突する場合は無言で更新せず、競合として作者へ提示する。

競合の解決操作は対象ごとに次を出す。

- hard契約との衝突: 「この場面を書き直す」「契約を編集・無効化する」「今回の採用本文だけ例外として残す」「誤検出として表示を閉じる」。
- revealed canonとの衝突: 「以前の正史を維持してこの場面を書き直す」「今回の本文を新しい正史としてretconする」「claim / rumorとして併存させる」。

競合解決は`CanonConflict.status`と対象canon/contractのrevisionを同じproject lock内で更新する。

- 「今回の採用本文だけ例外として残す」は`exception-accepted`へ遷移し、`CreativeContract.exceptions`へgeneration単位の`ContractException`を保存してから、該当canon patchを例外注記付きで適用する。
- `dismissed`は現在のバナーを一時的に抑えるだけであり、解決済み件数には数えない。矛盾候補のcanon patchをcleanな正史として適用せず、次回生成前の要確認一覧には残す。StoryStateには採用本文で起きた出来事を記録できるが、hard契約との関係を解消した扱いにはしない。作者が本当に本文側を残す場合は`exception-accepted`、検出が誤りなら競合内容を再分類したうえで`resolved`にする。
- exceptionを後から取り消した場合は競合をpendingへ戻し、該当正史を無言で削除せず再解決を要求する。

StoryStateとcanonは、採用本文1件につき**1回の構造化LLM抽出**から同時に作る。既存`updateStoryStateFromAcceptedScene`を「観測抽出」と「適用」に分離する。LLMは`NarrativeObservation[]`だけを正本として返し、StoryState patchとcanon patchは正規化済みobservationsからserver側が派生させる。LLMに二つの独立patchを同時生成させない。これにより、同じ台詞をStoryStateではfact、canonではclaimと別判定する経路を作らない。

処理手順は次とする。

1. `startStoryStateRefreshAfterAcceptance`の既存background jobを採用本文派生更新の入口として再利用する。
2. `accepted-derivations.json`に同じgenerationIdの結果が無ければ、関連する最大12件のcanonだけを添えて1回抽出する。
3. observationsを共通正規化・上限検査へ通し、StoryState/canonそれぞれの適用可能なserver内部patchへ変換してから、observationsと派生patchを`AcceptedNarrativeDerivation.status = 'extracted'`で先にsafe writeする。未検証のLLM出力を再試行キャッシュにしない。
4. project lockとStoryState lockの同一区間で、`StoryState.processedGenerationIds`に無ければstory patch、`LatentCanonStore.processedGenerationIds`に無ければcanon patchを適用する。
5. 両方の保存後にderivationを`applied`へ更新する。
6. 片側だけ保存されて失敗した場合は`partially-applied`と`ProjectState.storyStateRefresh.status = 'stale'`を残す。再試行はキャッシュ済みpatchを読み、未処理集合の側だけを適用する。モデルは再呼び出ししない。

`storyStateRefresh`は互換性のため採用本文派生job全体のpending/fresh/stale表示に共用する。canon専用の二つ目の鮮度stateは作らない。hard契約またはrevealed canonとの競合は適用失敗ではないためstaleにせず、`LatentCanonStore.pendingConflicts`へ永続化する。`ReaderState`へ`canonConflictCount`を追加し、Readerの状態バナーと作品設定の「要確認」一覧から対象場面・短い根拠・解決操作へ遷移できるようにする。console.warnだけで終わらせない。

既存の`calculateStoryStateBacklog` / `readStoryStateBacklog`は、StoryStateのprocessed集合だけを見る実装から、**採用済みgenerationがStoryStateまたはlatent canonのどちらか一方でも未処理なら返す共通backlog**へ変更する。derivationが`partially-applied` / `stale`のgenerationも必ずbacklogへ残す。両方のprocessed集合に入り、derivationが`applied`になった場合だけjobをfreshとする。これにより、StoryState側だけ保存済みの部分失敗を手動再抽出・再起動後回復から取りこぼさない。

### 6.4 採用取消・差し替え

正史は不変ではなく、根拠追跡可能であることを優先する。

- 採用取消時は、そのgenerationをevidenceから除く。
- 他の採用本文またはmanual evidenceが残る項目は維持する。
- evidence削除後は残ったevidenceの`disclosure`からstatusを再計算する。根拠をすべて失った項目は`baseStatusWithoutEvidence`へ戻す。すなわち、setup/on-demand由来は`provisional`、採用本文から新規抽出された項目は `retired: evidence-removed` になる。
- 取消対象generationをStoryStateとlatent canonの両`processedGenerationIds`から除き、そのgeneration由来のpending conflictを解決前なら取り下げる。accepted derivation recordは監査と再採用時の再利用のため削除せず`status = 'extracted'`へ戻す。同じ本文を再採用した場合はキャッシュ済みpatchを再適用し、モデルを再呼び出さない。
- 取消によって後続の採用本文と整合しなくなる場合は、自動で後続正史を消さず「再抽出が必要」と表示する。
- 現行の同一generation ID書き換えはNG局所リライトであり、既存StoryStateと同様にcanonも何もしない。局所表現置換は物語の事実を変えない前提とする。将来、事実を変え得る同一ID編集を導入する場合はNGリライトと別eventを定義し、そのeventだけaccepted derivationを無効化・再抽出する。
- 作者がrevealed項目を手動変更した場合、元evidenceは履歴として残し、manual evidenceを追加する。

### 6.5 進行中の追加補完

開始時に設定を作り切らない。追加補完は次のタイミングで行う。

- 採用後の状態抽出で、近く必要になりそうな空白が見つかったとき。
- 新しい人物・場所・組織が本文へ登場し、最低限の一貫性が必要になったとき。
- ユーザーの次回希望が `authorUndecided` またはopen threadへ近づいたとき。

原則として、追加補完は採用後の非同期処理へ同梱し、次回生成の待ち時間へ乗せない。補完が間に合わない場合、本文生成モデルが自然に作った新事実を採用後に抽出する。補完失敗だけで次回生成をブロックしない。

アプリは「まだ決めないこと」を埋めない。`StoryState.authorUndecided` にactiveな項目と意味的に重なる潜在設定を生成・注入しない。この重複判定だけの追加LLM呼び出しは作らず、潜在設定の関連選択・追加補完に使う既存の構造化プロンプトへactiveな`authorUndecided`を同梱し、該当項目を返さないよう指示する。

## 7. API・サービス境界

### 7.1 新規サービス

- `creativeContractService.ts`
  - 正規化、件数上限、競合検査、revision管理。
- `latentCanonService.ts`
  - 保存、関連選択、状態遷移、根拠追加・削除、退役、ロック。
- `acceptedNarrativeDerivationService.ts`
  - 採用本文からStoryState patchとcanon patchを1回で抽出し、generation単位でキャッシュ・冪等適用する。
- `roleplayCanonFoldService.ts`
  - 会話要約と同じfold呼び出しでsession canon patchを抽出・適用する。
- `contractVerificationService.ts`
  - hard契約検証、最大1回の修復、監査結果。

`storyStateService` は進行状態の正本を維持する。ただしLLM抽出は`acceptedNarrativeDerivationService`へ移し、1回の出力からStoryState適用関数とlatent canon適用関数を呼ぶ。StoryState用とcanon用の別モデル呼び出しを作らない。

### 7.2 新規API

```text
GET   /projects/:id/creative-contract
PUT   /projects/:id/creative-contract
GET   /projects/:id/canon-summary
POST  /projects/:id/canon/reveal
GET   /projects/:id/canon-conflicts
POST  /projects/:id/canon-conflicts/:conflictId/resolve
PATCH /projects/:id/canon/:canonId
POST  /projects/:id/canon/:canonId/lock
POST  /projects/:id/canon/:canonId/retire
POST  /projects/:id/canon/reextract
GET   /projects/:id/roleplay/sessions/:sessionId/canon-summary
POST  /projects/:id/roleplay/sessions/:sessionId/canon/:canonId/reveal
POST  /projects/:id/roleplay/sessions/:sessionId/canon/:canonId/promote
```

- `canon-summary` はshielded時に未公開項目の件数・カテゴリだけを返す。
- 潜在設定本文の取得は、`canon/reveal` の明示操作後に行う。
- 更新系はすべてrevisionを要求し、形式的な409を受けたclientは最新storeを再取得してからユーザー編集を再適用する。複数編集を古いrevisionのまま連続送信しない。
- creative contractのsemantic conflictは、初回`PUT`で409、競合候補、`conflictFingerprint`を返す。同じrevisionと`confirmConflictFingerprint`を付けた再`PUT`だけが競合を承知した保存になる。fingerprintが変わった場合は再確認する。
- `promote` は対象のsession canon、昇格先scope、現在のproject revisionを検証する。
- roleplayの`canon-summary`はopaqueな`canonId`、scope、`人物に関する未公開設定`のような非ネタバレlabelだけを返し、statement/excerptは返さない。作者がセッション設定詳細から項目を明示的に開いた場合だけ、`reveal`が当該1件のstatementとevidence previewを返す。
- APIエラーに潜在設定本文を埋め込まない。

### 7.3 ストレージ

`ProjectStorage` にcreative contract、latent canon、accepted derivationsのread/writeを追加し、file storageとbound storageを同時に実装する。契約へ追加した全メソッドは`PROJECT_STORAGE_METHODS`にも同時追加する。既存の網羅性型チェックを通し、所有権ガードとbound facadeを素通りするメソッドを作らない。

セットアップcommitでは次を一つの計画として作る。

- project
- world
- characters
- story state
- creative contract
- latent canon
- accepted derivations（初期値は空）

クイックセットアップも`setupSessionService.commitSetupSession`から`projectService.createProject`を呼ぶ既存経路に統一する。`CreateProjectBody`またはserver内部入力へ初期creative contract、latent canon、空accepted derivationsを追加し、`createProject`の書き込み列でproject/state/presets/characters/memories/world/storyStateと一緒に作る。途中失敗は既存どおりプロジェクトディレクトリ全体を`deleteProject` / `deleteProjectDir`で除去する。ファイル単位のrollbackを新設しない。

setup commit後段のmemories/storyState保存が失敗した場合も、現行どおり作成済みプロジェクトディレクトリ全体を削除する。潜在設定生成だけが事前に失敗した小説は、空latent storeを正規のcommit planとして渡すため部分ファイル欠損にはならない。

## 8. ロールプレイ固有設計

### 8.1 セッション開始

セッション開始時に次をsnapshotする。

- activeなhard / soft creative contract
- manual lockされた設定
- 対象キャラクターと舞台に関連するrevealed / latent canon
- 既存の人物・世界・ユーザーペルソナ

進行中の会話へプロジェクト設定変更を自動反映しない。現行の `settingsChanged` と「現在の設定で新しい会話」導線を維持する。

`buildSettingsFingerprint`には、従来のroleplay preset・base/custom promptに加え、active creative contractと選択済みcanon snapshotをID順で正規化したhashを含める。現在値側のfingerprintも同じ関連選択規則で計算し、契約または対象canonの変更を`settingsChanged`で検知する。

### 8.2 会話中の正史

- 完了したcharacter messageを保存するたびに別のLLM抽出は行わない。通常のsession canon更新は、既存の`conversationSummary` foldが走るタイミングで、同じLLM出力へ`sessionCanonPatch`を追加して行う。
- `sessionCanonThroughMessageId`を要約cursorと同じfold境界まで進め、同じmessageを二重抽出しない。要約だけ成功・canonだけ失敗する別呼び出しは作らない。
- まだfoldされていない直近messageはsession canonへ即時反映されない。表示上は会話本文そのものを正とし、canon summaryの遅延を許容する。
- user messageが世界の客観的事実を宣言しても、自動で `fact` にしない。まずユーザーキャラクターの `claim` として扱う。
- 再生成・停止後訂正で未foldのメッセージが置換された場合はcanon更新不要とする。将来fold済みmessageを編集できるようにする場合だけ、該当foldから要約とsession canonを再構築する。
- 会話要約で省略されても、session canonのevidenceは維持する。
- アーカイブ後も読み返しの整合性のため保存するが、新セッションへ自動継承しない。
- 作者がfold前に「作品設定へ残す」を選んだ場合だけ、その選択操作を起点に対象messageを1回抽出できる。この明示操作以外ではmessage単位の追加LLM呼び出しを行わない。

### 8.3 作品設定への昇格

各session canon項目に、設定詳細から「作品設定へ残す」を表示する。会話バブルごとに常時ボタンを出して没入を壊さない。

設定詳細の初期表示は`canon-summary`だけを使う。作者が非ネタバレlabelを選んだときに対象`canonId`の`reveal`を呼び、内容確認後に同じIDで`promote`する。`RoleplaySessionView`へsession canon本文を戻して実装を簡略化してはならない。

昇格時は次をプレビューする。

- 残す内容
- `fact` / `claim` / `belief` / `rumor` の区分
- 既存設定との競合
- 次の新規セッションから反映されること

既存セッションのsnapshotは書き換えない。競合がある場合は自動昇格せず、既存項目の置換・別のclaimとして併存・キャンセルを選ばせる。

昇格時は、project側のevidenceへ`kind: 'roleplay-promotion'`、必須の短いexcerpt、昇格日時をコピーする。元`sessionId` / `messageId`は監査用optional参照に留め、参照先を再読込しなくても根拠を表示できる形にする。現行の`DELETE /roleplay/sessions/:sessionId`は物理削除ではなくarchiveだが、将来の物理削除やデータ整理後も昇格済みcanonをダングリングさせない。

## 9. 既存データとの互換性

- 既存プロジェクトはcreative contractなし、latent canonなしで従来どおり動く。
- `coreConcept`、`world.md`、`characters.json` は既存の作者指定設定として優先する。自動で潜在設定へ移さない。
- 既存のStoryStateはrevealed canon相当の進行情報として生成プロンプト上の優先度を維持する。
- 既存の`Character.secrets`は作者指定のmanual canonとして扱うが、新ストアへ自動複製しない。
- 「作品の約束をAIで抽出」は任意の移行操作とし、候補を作者が確認するまでhardにしない。
- 既存setup sessionのschemaVersion 1/2は読み取り可能にする。新しいクイックセットアップ項目はoptionalで追加するか、schemaVersion 3へ正規化する。
- 既存roleplay sessionには契約・canon snapshotがないため、従来プロンプトで継続する。途中から現在設定を注入しない。
- 作品複製ではcreative contractだけを複製し、latent canon台帳とaccepted derivationsは複製しない。現行複製はgenerations/episodesをコピーせずStoryStateをコピーするため、複製先の公開済み進行情報は既存StoryStateをrevealed相当として使う。provisional / foreshadowedは失われるが、存在しないgeneration evidenceをmanualへ偽装するより単純で安全である。複製先のlatent storeとaccepted derivationsは空で開始し、以後の進行から再補完する。

## 10. 失敗モードと対策

### 10.1 見えない設定が物語を支配する

対策:

- 潜在設定はhard制約にしない。
- 今回に関連する少数だけを注入する。
- `foreshadowed` でも回収義務を持たせない。
- 未使用provisionalを自動退役できるようにする。

### 10.2 後付けに見える

本文で突然revealedへ上げず、必要な場合は先に自然な示唆を作る。ただし、すべての設定に伏線を強制しない。重要度の高いhistory / identityだけに「示唆を挟む」推奨を付ける。

### 10.3 台詞を真実として保存する

`epistemicStatus` を必須にし、台詞・噂・内心は既定でfactにしない。抽出テストに嘘、誤解、記憶違い、比喩、冗談を含める。

### 10.4 hard契約が互いに衝突する

保存時に競合候補を検出した初回`PUT`は409と`conflictFingerprint`を返す。ユーザーは契約文を条件付きの一文へ編集するか、競合候補を承知してfingerprint付き再`PUT`で保存できる。semantic判定の偽陽性を理由に保存不能へしない。生成時には作成順や配列順で勝者を決めない。

### 10.5 修復で文章が壊れる

修復は最大1回、問題箇所と周辺だけを対象にする。修復後も失敗する場合は警告付きドラフトとして止め、無限再試行しない。元本文も診断用に保持するが通常UIへ二重表示しない。

### 10.6 正史変更が過去本文と衝突する

revealed canonの変更を無言で適用しない。根拠場面を示し、「設定だけ変更」「影響する場面の書き直し案を作る」「キャンセル」を選ばせる。

### 10.7 APIコストと待ち時間が増える

- 初期補完は1回最大8件。
- semantic verifierはhard契約がある場合だけ呼ぶ。
- 修復は最大1回。
- 追加補完は採用後の非同期処理へ同梱する。
- 小説のStoryState/canon抽出は1回の構造化呼び出しへ統合する。
- ロールプレイのsession canon抽出は既存conversation summary foldへ同梱し、通常messageごとの追加呼び出しを作らない。
- 検証・補完の呼び出し回数と推定トークンをtelemetryへ記録する。

### 10.8 ネタバレがログへ出る

注入された潜在設定は、診断フラグに関係なく常時保存される`generations/{generationId}.prompt.txt`へ含まれる。加えて、開発用prompt dump、推論ログ、crash logにも未公開設定が含まれ得る。作品データの共有・バックアップ案内では`generations/*.prompt.txt`を明記し、診断ログ有効時だけの注意に限定しない。通常のエラー本文と通知には潜在設定本文を含めない。

## 12. テスト方針

### 12.1 型・正規化

- AI提案からhard契約を保存できない。
- hard 8件、soft 12件、各文字数上限を超える入力を拒否する。
- hard render合計4,000字を超える入力を拒否する。
- 旧ファイル欠損を空ストアとして読める。
- unknown enum、重複ID、空statement、根拠なしrevealedを安全に補正または拒否する。
- `baseStatusWithoutEvidence`欠損の旧項目はsourceに応じ、setup/on-demandなら`provisional`、generation/roleplayなら`retired`へ補正する。
- `processedGenerationIds`と`pendingConflicts`欠損は空配列へ正規化する。
- `exceptions`欠損は空配列になり、別project・未採用generation・不存在contractを参照するexceptionを拒否する。
- `ProjectStorage`の新規メソッドが`PROJECT_STORAGE_METHODS`から欠けると網羅性型チェックが失敗する。

### 12.2 プロンプト

- hard契約が常にrevealed / latent / softより前に出る。
- hard契約が予算縮小で省略されない。
- hard required sectionの最低予約が総予算を超えた場合、既存`prompt_budget_exceeded`になりモデルを呼ばない。
- soft契約と既存preference memoryが一つの経路へ合流し、同じ本文を二重表示しない。
- `authorUndecided` と競合するlatent項目を注入しない。
- 無関係な潜在設定を全件注入しない。
- canon照合候補が最大12件に制限される。
- 12件の外に同じscope/subject/normalizedStatementを持つactive canonがあれば、適用前の全件検査で既存IDへmergeされる。
- claim / belief / rumorを客観的factとして描画しない。
- roleplay sessionが開始後のproject設定変更を取り込まない。

### 12.3 状態遷移

- ドラフト生成だけではlatent canonが変化しない。
- 採用でprovisionalからforeshadowed / revealedへ遷移する。
- 台詞の明示はclaimになり、factにならない。
- 採用取消で根拠が外れ、他の根拠がなければ前状態またはretiredへ戻る。
- manual evidenceが残る項目は採用取消で消えない。
- accepted本文がprovisionalと衝突した場合、本文を優先してlatentをretiredにする。
- revealed canonとの衝突は無言で上書きしない。
- 同じgenerationの再抽出を二重適用しない。
- StoryState/canonが1回の構造化抽出から作られ、別々のモデル呼び出しにならない。
- StoryState/canon patchが同じ正規化済み`NarrativeObservation[]`からserver側で派生し、LLMの独立patchを受け取らない。
- storyState保存後・canon保存前の失敗を`partially-applied`とstaleで記録し、再試行でモデルを呼ばずcanon側だけ適用する。逆順の部分失敗も同様に回復する。
- 共通backlogはStoryState/canonの片側だけ未処理のgenerationを残し、両方適用済みになるまでfreshにしない。
- pending conflictが再起動後も残り、consoleだけで消えない。
- NG局所リライトではcanon抽出とprocessed集合を変更しない。
- 採用取消で両processed集合と未解決conflictからgenerationが外れ、再採用時は保存済みderivationを再利用する。
- roleplay summary foldが`sessionCanonThroughMessageId`を同じcursorまで進め、再実行で二重適用しない。
- roleplay promotion evidenceはsession再読込なしで必須excerptを表示できる。

### 12.4 契約検証

- hard項目なしではsemantic verifierを呼ばない。
- verifier / 再検証はactive model・30秒timeout、局所修復はactive model・120秒timeoutになる。
- fail時の修復は1回を超えない。
- 修復成功時だけ通常ドラフトとして返す。
- 修復失敗時はstrict / fastごとの警告状態になる。
- ユーザーが警告を越えて採用しても契約を自動変更しない。
- hard同士の競合を配列順で解決しない。
- 初回競合PUTは409になり、同一revision・一致fingerprint付き再PUTだけが保存される。
- hard契約違反を例外採用するとgeneration単位の`ContractException`が残り、契約は将来の生成で有効なままになる。
- conflictをdismissしただけでは矛盾canon patchがcleanな正史として適用されない。

### 12.5 UI

- shielded時に未公開本文が初期HTML、通常APIレスポンス、通知へ出ない。
- `RoleplaySessionView`のJSONへ`sessionCanon`本文が構造上含まれない。
- roleplay canon summaryはopaque ID/非ネタバレlabelだけを返し、明示revealした1件だけ本文を返す。
- 明示操作なしに未公開設定を展開しない。
- manual lock解除は作者操作だけで行える。
- foreshadowed / revealed編集時に根拠場面を表示する。
- roleplay昇格は明示確認を要求し、既存sessionを変更しない。
- strict時も`streamingEnabled: true`なら本文chunkを即時表示し、phaseを併記する。修復時は`replace`で確定本文へ差し替える。
- canon競合件数がReaderに表示され、設定画面の永続一覧へ遷移できる。
- quickからfullへ切り替えても同じsetup sessionのdraft・messages・locksが残る。
- creative contract/canon変更でroleplayのfingerprintが変わり、未変更時は安定する。

### 12.6 受け入れシナリオ

1. 一文の希望だけで小説を作成し、詳細設定画面を経由せず最初の生成へ進める。
2. 「護衛は裏切らない」をhard契約にした作品で、裏切りを含む候補が通常本文として確定表示されない。
3. アプリが作った人物の過去は設定画面で既定非表示だが、本文で明らかになった後は公開済み設定に現れる。
4. 人物が嘘をつく場面を採用しても、嘘の内容自体はfactへ昇格しない。
5. 示唆だけした潜在設定を後から別の真相へ変更できる。
6. 明示済み正史を変更すると、影響場面を示して確認される。
7. 採用取消で、その場面だけを根拠にした正史が残り続けない。
8. ロールプレイで生まれた設定は、明示昇格しない限り別セッションへ入らない。
9. ロールプレイの通常40 message以下では追加canon抽出を呼ばず、summary fold時に同梱される。
10. 昇格済みロールプレイ設定は元sessionをarchiveしてもコピー済みexcerptから根拠を表示できる。
11. 契約または関連canonを変更すると既存roleplay sessionの`settingsChanged`がtrueになる。
12. 複製先にlatent canon/accepted derivationsは持ち越されず、creative contractとStoryStateだけが期待どおり引き継がれる。
13. クイックセットアップのlatent seedだけが失敗しても、小説は空store付きでcommitできる。
14. 診断設定に関係なく、未公開設定が`generations/*.prompt.txt`へ含まれ得ることが分かる。

## 13. 要確認事項

以下は実装前にプロダクト判断を確定する。括弧内は本設計書の推奨値である。

1. **初期補完方式:** 開始時に裏設定を作り切るか、薄い初期補完と進行中補完を組み合わせるか。推奨: **ハイブリッド。開始時最大8件、その後は必要時だけ追加。**

2. **hard契約の上限:** 推奨: **promise / prohibition合計8件、UI上は3〜5件を推奨。**

3. **既定のネタバレ表示:** 推奨: **`shielded`。件数とカテゴリだけ表示。**

4. **契約検証中の本文表示:** 推奨: **hard契約がある作品は`strict`。暫定本文を即時表示し、検証後に確定本文へ収束。**

5. **初回リリース対象:** 小説とロールプレイを同時実装するか。推奨: **小説を先行し、データ境界が安定してからロールプレイへ展開。**

6. **ロールプレイ事実の作品昇格:** 推奨: **セッション詳細から1件ずつ明示昇格。一括・自動昇格なし。**

7. **hard契約違反の最終選択:** 修復失敗本文を完全に破棄するか、警告付きで作者が見られるようにするか。推奨: **既定では隠し、作者が「問題箇所を確認」を選んだ場合だけ表示。明示確認で採用可能。**
