# ロールプレイ会話要約安定化 設計書

作成日: 2026-08-31  
対象バージョン: 次期ベータ  
状態: 実装前  
実装後の扱い: 実装・受け入れ確認後に `docs/design/archive/` へ移動する。

## 0. 結論

ロールプレイ会話の要約処理を、次の5点で安定化する。

1. 要約を明示的な JSON タスクとして呼び、DeepSeek V4 の thinking を無効にする。
2. 出力上限、空本文、JSON 不正、構造不正の場合だけ、最大1回自動再試行する。
3. JSON タスクの共通リクエスト設定を一か所へ集約し、用途ごとに reasoning の有効・無効を必須指定にする。
4. 要約が返し得る JSON 全体の大きさに合わせて、目標字数と最大出力トークン数を分離して設定する。
5. 同期要約が必要になる前に、30メッセージを目安としてバックグラウンド要約を開始する。

最重要の不変条件は、要約が完全に成功するまで `conversationSummary`、`relationshipState`、`sessionCanon`、`summaryThroughMessageId`、`sessionCanonThroughMessageId` のどれも進めないことである。失敗直前のユーザー発言は既存どおり保存し、「もう一度応答をもらう」から同じ発言への応答生成を再開できる。

## 1. 背景と再現結果

### 1.1 発生した事象

2026-08-31、`deepseek-v4-flash` を使用したロールプレイで、次のエラーが表示された。

> 会話履歴の要約に失敗しました。時間をおいて再試行してください。

同一セッションのログでは、バックグラウンド要約と次ターン開始時の同期要約が連続して次の状態になっていた。

- `label: roleplay.summaryFold`
- `finishReason: length`
- `parseFailure: empty_text`
- モデル: `deepseek-v4-flash`

要約対象プロンプトは生成され、API 呼び出しにも到達している。通信エラー、API キー不足、タイムアウトではない。

### 1.2 根本原因

`performSummary` はモデルへ JSON オブジェクトだけを返すよう指示しているが、`runNonStreaming` へ次を渡していない。

- `responseMimeType: 'application/json'`
- `reasoningMode: 'disabled'`
- `maxOutputTokens: JSON_TASK_MAX_OUTPUT_TOKENS`

このため `DeepSeekAdapter` は `deepseek-v4-flash` の非 JSON 既定経路として thinking を有効にし、`reasoning_effort: high` を送る。`outputLength: 1600` から導出された出力枠を reasoning が使い切り、最終本文 `content` が空のまま `finishReason: length` で終了した。

### 1.3 現在のデータ状態

今回のセッションでは、失敗したターンのユーザーメッセージは保存済みである。一方、要約カーソルは前回成功位置のままなので、履歴の欠落や不完全な要約の採用は起きていない。

これは現在の「ユーザー発言を先に保存し、要約成功後にだけ派生フィールドを原子的にマージする」方針が機能した結果であり、本改修でも維持する。

## 2. 目的と非目標

### 2.1 目的

- DeepSeek V4 Flash で要約本文が reasoning によって空になる事象を防ぐ。
- 構造化 JSON の一時的な不成立を、最大1回の安全な再試行で回復する。
- JSON タスクの設定漏れを新しい呼び出し経路で起こしにくくする。
- 要約の期待出力量と API の最大出力枠を一致させる。
- 通常ターンの送信時に同期要約が発生する頻度を下げる。
- 要約失敗時も履歴、revision、要約カーソル、session canon の整合性を維持する。

### 2.2 非目標

- 要約アルゴリズムや要約文体そのものの全面変更
- ロールプレイ本文の生成モデルを自動的に別モデルへ切り替えること
- 別プロバイダーへの自動フォールバック
- ユーザー向けエラー画面の全面再設計
- 保存スキーマの変更や既存セッションの一括再要約
- 要約と session canon 抽出を別々の API 呼び出しへ分割すること
- DeepSeek API 以外のプロバイダー固有挙動の変更

## 3. 用語と不変条件

### 3.1 用語

| 用語 | 意味 |
|---|---|
| 同期要約 | ターン生成前に予算超過を解消するため、利用者を待たせて実行する要約 |
| バックグラウンド要約 | キャラクター応答保存後に、次ターンへ備えて非同期実行する要約 |
| fold 対象 | 既存要約へ畳み込む古いメッセージ群 |
| 直近保持 | 要約せず生の会話として残す新しいメッセージ群 |
| JSON タスク | モデル出力を機械解析し、構造化データとして採用する生成処理 |
| 利用可能な要約結果 | `finishReason` が完全終了で、JSON と必須フィールドの解析が成功した結果 |

### 3.2 維持する不変条件

1. ユーザーメッセージの先行保存契約を変えない。
2. 要約生成中は session mutex を保持しない。
3. 要約マージ時だけ mutex を取得し、snapshot の `revision` と `summaryThroughMessageId` が一致するときだけ保存する。
4. 要約失敗時は要約関連フィールドを一つも更新しない。
5. 初回と再試行の結果を混ぜない。採用した一方の JSON 全体だけを使う。
6. 同一 `performSummary` 内のモデル呼び出しは最大2回とする。
7. reasoning 本文、API キー、完全なプロンプトを新しい通常ログへ追加しない。
8. 同期要約はバックグラウンド要約のクールダウンに妨げられない。

## 4. 設計方針

### 4.1 対策1: 要約を明示的な JSON タスクとして呼ぶ

`performSummary` のモデル呼び出しには、次を必ず設定する。

```ts
{
  responseMimeType: 'application/json',
  reasoningMode: 'disabled',
  maxOutputTokens: JSON_TASK_MAX_OUTPUT_TOKENS,
}
```

理由:

- 要約は自由文生成ではなく、`summary`、`relationshipState`、`sessionCanon` を持つ JSON の抽出・圧縮タスクである。
- DeepSeek V4 では JSON 指定と `reasoningMode: disabled` により thinking を明示的に止められる。
- reasoning を使わないため、出力枠を最終 JSON のために使える。
- `responseMimeType` を理解する他アダプタでも、既存の構造化出力経路を利用できる。

DeepSeek のモデル名を `roleplaySessionService` 内で判定しない。要約は全プロバイダーで同じ JSON タスク契約を使い、プロバイダー固有の body 変換はアダプタへ任せる。

### 4.2 対策2: 最大1回の自動再試行

#### 4.2.1 再試行条件

初回結果が次のいずれかに該当するときだけ再試行する。

- `finishReason === 'length'`
- `finishReason` は完全終了だが `text.trim()` が空
- JSON の開始・終了区切りを取得できない
- JSON.parse に失敗する
- JSON だが `summary` が非 string または空
- JSON だが `sessionCanon` が配列ではない

次は再試行しない。

- API エラー
- タイムアウト
- `content_filter`
- 利用者キャンセル
- `no_fold_target`
- snapshot が stale になっただけのケース

API エラーやタイムアウトを同じ呼び出し内で再試行しない理由は、待ち時間と二重課金を無条件に増やさず、既存の「利用者が再試行できるエラー」契約を維持するためである。

#### 4.2.2 再試行リクエスト

再試行では、system prompt、要約対象、既存要約、既存 relationship、session canon 候補、モデル名を変えない。次だけを変更する。

- `debugLabel`: `roleplay.summaryFold.retry`
- `temperature`: `0.1`
- user prompt の末尾に、完全な JSON を閉じることと `sessionCanon` が無い場合も空配列を出すことを再度明記する

JSON モード、thinking 無効、最大出力トークン数は初回と同じにする。再試行時に reasoning を有効へ戻してはならない。

#### 4.2.3 採用条件

初回・再試行とも、次をすべて満たした場合だけ採用する。

- `finishReason === 'stop'`
- `parseSummaryOutput` が成功する
- `summary` が空でない
- `sessionCanon` が配列である

`finishReason === 'length'` の結果は、偶然 JSON.parse できても採用しない。末尾の配列やフィールドが欠けていないことを保証できないためである。

再試行も失敗した場合は、初回の不完全な結果へ戻らず `empty_result` または `llm_failed` として扱う。

#### 4.2.4 責務の配置

再試行はアダプタではなく `roleplaySessionService` が行う。

- 要約 JSON の必須フィールドを判断できるのは要約サービスである。
- アダプタ内で再試行すると、同じアダプタを使う別タスクまで二重実行される。
- `performSummary` を手動再構築、同期要約、バックグラウンド要約が共有しているため、一か所で全経路を修正できる。

### 4.3 対策3: JSON タスク設定の共通化

#### 4.3.1 共通関数

新規ファイル `src/server/services/jsonTaskPolicy.ts` に、JSON タスク用リクエストを構築する純粋関数を追加する。

想定インターフェース:

```ts
export interface JsonTaskPolicyOptions {
  reasoningMode: 'enabled' | 'disabled';
  maxOutputTokens?: number;
}

export function applyJsonTaskPolicy(
  request: AdapterGenerateRequest,
  options: JsonTaskPolicyOptions
): AdapterGenerateRequest;
```

戻り値には必ず次を設定する。

```ts
{
  ...request,
  responseMimeType: 'application/json',
  reasoningMode: options.reasoningMode,
  maxOutputTokens:
    options.maxOutputTokens ?? JSON_TASK_MAX_OUTPUT_TOKENS,
}
```

`reasoningMode` に既定値を設けない。JSON だから常に推論不要とは限らず、AI相談のように JSON と推論を意図的に併用するタスクがあるため、呼び出し側に選択を強制する。

#### 4.3.2 共通化する範囲

本改修では少なくとも次を共通関数経由へ移す。

- `roleplay.summaryFold`: `disabled`
- `amplifier.choices`: `disabled`
- setup の草案抽出・クイックプラン: 現行意図に合わせて `disabled`
- refine scan、物語状態抽出、生成後保守、文体分析などの機械抽出: `disabled`
- refine chat の初回と再試行: 現行設計に合わせて初回 `enabled`、再試行 `disabled`

個別タスクが現在 `4_096`、`6_000`、`8_192` など独自の `maxOutputTokens` を使っている場合は、その値を options へ明示して維持する。共通化を理由に全タスクを40,000へ揃えない。

#### 4.3.3 共通化しない責務

共通関数は次を行わない。

- API 呼び出し
- 再試行
- タスク固有 JSON の解析
- `finishReason` の採用判定
- session や project の保存
- provider/model の自動切り替え

これにより、共通化は「リクエスト設定漏れの防止」に限定し、各サービスの整合性責務を保つ。

### 4.4 対策4: 要約出力枠の見直し

#### 4.4.1 現在の不整合

現行は `outputLength: 1600` だが、要約 JSON は次を含み得る。

- 最大6,000字の `summary`
- relationship の数値、呼び方、最大8件の約束、最大8件の未解決事項
- 最大20件として解析する `sessionCanon` patch

1,600字は JSON 全体の期待値として小さすぎる。また、`outputLength` から最大トークン数を推定すると、thinking モデルでは推論だけで枠を使い切る可能性がある。

#### 4.4.2 新しい定数

`roleplaySessionService.ts` に次を置く。

```ts
const ROLEPLAY_SUMMARY_TARGET_OUTPUT_CHARS = 12_000;
const ROLEPLAY_SUMMARY_RETRY_TEMPERATURE = 0.1;
```

最大出力トークン数は共通の `JSON_TASK_MAX_OUTPUT_TOKENS`、現在値40,000を使う。

役割を分離する。

| 値 | 役割 |
|---|---|
| `ROLEPLAY_SUMMARY_MAX_CHARS = 6000` | 保存する要約本文の上限 |
| `ROLEPLAY_SUMMARY_TARGET_OUTPUT_CHARS = 12000` | JSON全体の通常期待量・診断値 |
| `JSON_TASK_MAX_OUTPUT_TOKENS = 40000` | reasoningを含まないJSON生成のAPI上限 |
| session canon 最大20件 | 解析・保存時の防御上限 |

`maxOutputTokens` を明示するため、`outputLength` は API のハード上限導出には使われない。プロバイダー固有の上限が40,000未満なら、既存の `resolveMaxOutputTokens` が clamp する。

#### 4.4.3 プロンプト側の出力量抑制

system prompt に次を明示する。

- `summary` は6,000字以内
- `sessionCanon` は今回追加・更新する差分だけ
- 既存項目の言い換え重複を作らない
- `sessionCanon` は最大20件
- 該当項目がなければ空配列

出力枠を広げても冗長化しないよう、生成指示とパーサ上限を一致させる。

### 4.5 対策5: バックグラウンド要約を早める

#### 4.5.1 soft threshold と hard threshold の分離

現行の40件という値は、バックグラウンド起動条件と同期要約の予算判定を兼ねている。これを分離する。

```ts
const ROLEPLAY_BACKGROUND_SUMMARY_THRESHOLD = 30;
const ROLEPLAY_SYNC_SUMMARY_THRESHOLD = 40;
```

- キャラクター応答保存後、要約カーソル以降が30件以上ならバックグラウンド要約を試みる。
- ターン開始時、40件超または既存の文字数・プロンプト予算超過なら同期要約を実行する。
- 要約成功後は既存どおり新しい方から最大20件・最大16,000字を直近履歴として残す。

30件を選ぶ理由:

- 通常の user/character 一往復で2件増えるため、40件まで約5往復の余裕がある。
- バックグラウンド要約が一度失敗しても、次ターンですぐ同期要約へ到達しにくい。
- 20件保持との差が10件あり、要約APIを毎ターン呼び続けにくい。

文字数の hard threshold 16,000字は維持する。文字数の soft threshold は本改修では追加しない。短い件数でも非常に長い発言がある場合は、既存の同期予算判定を正とする。

#### 4.5.2 バックグラウンド失敗のクールダウン

30件到達後に要約が失敗すると、成功するまで毎ターンAPIを呼ぶ可能性がある。これを防ぐため、プロセス内に次を持つ。

```ts
const ROLEPLAY_BACKGROUND_SUMMARY_FAILURE_COOLDOWN_MS = 60_000;
const backgroundSummaryRetryNotBefore = new Map<string, number>();
```

- バックグラウンド要約が `llm_failed` または `empty_result` で終わったら、同セッションの次回バックグラウンド起動を60秒抑制する。
- 成功時はエントリを削除する。
- 同期要約はクールダウンを参照しない。
- アプリ再起動で消えてよく、保存スキーマへ追加しない。
- `__resetInFlightForTesting` で map を clear する。

## 5. 処理フロー

### 5.1 通常ターン

```text
ユーザー発言を先行保存
  ↓
同期予算判定
  ├─ 40件以下かつ文字数・プロンプト予算内
  │    └─ 要約せず本文生成へ
  └─ 超過
       ↓
     JSON + thinking disabled + 40,000 tokens で要約
       ↓
     stop かつ完全なJSON？
       ├─ はい → snapshot一致時だけ要約を原子的に保存
       └─ いいえ
            ├─ length / empty / parse failure
            │    └─ 低temperature・補強指示で1回だけ再試行
            │         ├─ 成功 → snapshot一致時だけ保存
            │         └─ 失敗 → summary_failed、ユーザー発言は保持
            └─ API error / timeout / filter → 再試行せず summary_failed
  ↓
ロールプレイ本文を生成・保存
  ↓
同期要約をしていなければバックグラウンド要約を予約
```

### 5.2 バックグラウンド要約

```text
キャラクター応答保存
  ↓
要約カーソル以降が30件以上？
  ├─ いいえ → 終了
  └─ はい
       ↓
     in-flight または失敗クールダウン中？
       ├─ はい → 終了
       └─ いいえ → performSummary（最大2呼び出し）
                    ↓
                  成功かつsnapshot一致？
                    ├─ はい → 原子的に保存、クールダウン解除
                    └─ いいえ → 保存せず終了
                                 LLM/解析失敗だけ60秒クールダウン
```

## 6. 状態整合性とエラー処理

### 6.1 初回と再試行の間

- モデル出力はメモリ上だけに保持する。
- 初回失敗時に session へ途中結果を書かない。
- 再試行時にユーザーメッセージや revision を追加しない。
- 初回と再試行で fold 対象を再取得しない。同じ snapshot を使う。

### 6.2 要約成功時

既存の `mergeSummaryIfCursorUnchanged` と `buildMergedSessionAfterSummary` を正本とする。一回の書き込みで次を更新する。

- `conversationSummary`
- `summaryThroughMessageId`
- `summaryUpdatedAt`
- `relationshipState`
- `sessionCanon`
- `sessionCanonThroughMessageId`
- `derivedMemoryStatus`

派生更新なので revision は進めない。

### 6.3 要約失敗時

- 同期要約: `summary_failed` を返し、キャラクター本文生成へ進まない。
- バックグラウンド要約: 利用者へエラーを出さず、警告ログとクールダウンだけを残す。
- どちらも要約カーソルを進めない。
- 末尾が保存済みユーザーメッセージなら、UI の「もう一度応答をもらう」で同じ入力を再利用する。

### 6.4 stale 結果

モデル呼び出し中に別操作で revision または要約カーソルが変わった場合は、初回・再試行の成否にかかわらず結果を捨てる。stale はモデル失敗ではないため、バックグラウンド失敗クールダウンを設定しない。

## 7. ログと診断

初回・再試行のログには次を含める。

- `projectId`
- `sessionId`
- `sessionMode`
- provider / model
- `label`
- attempt: `initial` / `retry`
- `finishReason`
- `parseFailure`
- `debugInfo` がある場合は既存の短い診断
- `rawUsage` がある場合はトークン数だけ

含めないもの:

- API キー
- reasoning 本文
- 要約対象会話の全文
- system prompt / user prompt の通常ログへの複製

開発時の prompt dump は既存の `CHAPTERFLOW_DEV_DIAGNOSTICS` 契約に従う。再試行は `roleplay.summaryFold.retry` として区別できるようにする。

## 9. テスト計画

### 9.1 JSONタスク共通ポリシー

1. `responseMimeType` が常に `application/json` になる。
2. reasoningMode が呼び出し側指定どおりになる。
3. token 未指定時は40,000になる。
4. 個別 token 上限を渡した場合は維持される。
5. system prompt、user prompt、temperature、timeout、modelNameを変更しない。

### 9.2 要約初回リクエスト

1. `roleplay.summaryFold` が JSON モードで呼ばれる。
2. `reasoningMode: disabled` になる。
3. `maxOutputTokens` が `JSON_TASK_MAX_OUTPUT_TOKENS` になる。
4. `outputLength` が12,000になる。
5. DeepSeek V4 Flash の実 request body が `thinking: disabled` と JSON response format を含む。

### 9.3 再試行

1. 初回成功なら1回だけ呼ぶ。
2. `length` なら、初回JSONが読めても再試行する。
3. 空本文なら再試行する。
4. JSON parse failureなら再試行する。
5. `summary` 空なら再試行する。
6. `sessionCanon` 欠落なら再試行する。
7. retry は低temperature、専用label、thinking disabledで呼ぶ。
8. retry 成功時はretry結果だけを保存する。
9. retry 失敗時は初回結果を保存しない。
10. error / timeout / content_filterでは同一処理内の再試行を行わない。
11. モデル呼び出し回数が最大2回を超えない。

### 9.4 整合性

1. 要約失敗後も保存済みユーザーメッセージが残る。
2. 要約失敗後に要約カーソルが進まない。
3. `conversationSummary` だけが更新される部分成功を作らない。
4. retry 中にrevisionが変わったら結果を捨てる。
5. retry 後の「もう一度応答をもらう」でユーザー発言が重複しない。
6. background と sync が競合しても一方のstale結果を捨てる。

### 9.5 早期バックグラウンド要約

1. 29件ではモデルを呼ばない。
2. 30件でバックグラウンド要約を開始する。
3. 成功後に直近20件を残す。
4. 同じsessionのin-flight中は二重起動しない。
5. 失敗後60秒以内はbackgroundを再起動しない。
6. 失敗後でもsync要約は実行できる。
7. staleはクールダウン対象にしない。
8. テスト用resetでcooldown mapも消える。

## 12. リスクと対策

| リスク | 対策 |
|---|---|
| JSONモード非対応モデルでエラーになる | 既存アダプタの `supportsJsonResponseFormat` とプロバイダー固有実装を正本にする |
| 再試行で待ち時間・費用が増える | 成功時は再試行せず、最大1回、API error/timeoutは対象外にする |
| 40,000 token設定で無駄な長文が増える | thinking無効、summary 6,000字、canon差分最大20件をプロンプトで固定する |
| 30件到達後にbackgroundが毎ターン失敗する | 60秒クールダウンを入れ、syncは妨げない |
| 共通化で既存JSONタスクの挙動が変わる | reasoningとtoken上限を各呼び出しで明示し、移行前後のrequestテストを追加する |
| lengthだが解析可能なJSONを採用して欠落する | finishReasonがstopの結果だけを採用する |
| retry中に履歴が更新される | 既存のrevision・summary cursor一致検査でstale結果を捨てる |
| アプリ再起動でcooldownが消える | cooldownは費用抑制だけの補助状態とし、永続化しない |

## 13. 実装時の注意

- 現在の作業ツリーにある利用者の変更を巻き戻さない。
- `performSummary` は手動記憶再構築、同期要約、バックグラウンド要約で共有される。個別経路に重複した再試行を追加しない。
- `parseSummaryOutput` と `classifySummaryParseFailure` の判定規則を別実装に分裂させない。再試行判定用の一回の解析結果を採用判定にも再利用する。
- `reasoningEffort: low` を DeepSeek V4 の軽量thinking対策として使わない。要約ではthinking自体を無効にする。
- `JSON_TASK_MAX_OUTPUT_TOKENS` を増やすだけの修正にしない。thinking無効とJSON指定が根本対策である。
- バックグラウンド要約の早期化だけを先に出荷しない。根本原因が残ったままAPI失敗回数を増やすため、対策1〜4を先に実装する。
