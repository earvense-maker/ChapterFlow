# 見せない面廃止・ロールプレイ公開状態整合性 設計書

作成日: 2026-08-11
対象バージョン: 未定（0.1.0-beta.11 以降を想定）
実装後の扱い: 実装と受け入れ確認の完了後 `archive/` へ移動する。

## 0. 結論

`Character.secrets` と、画面上の「見せない面」を特別な人物設定項目として廃止する。

人物の内面・普段表に出にくい性質は通常の `traits` または `description` で表現し、公開時期を管理する必要がある事実は `latent canon`、会話中に明かされた事実は `session canon` で扱う。人物設定に「自分からは明かさない」という恒久的な生成指示を保存しない。

既存の `secrets` データは移行しない。別項目への自動複製、AIによる再分類、警告表示、移行UIは作らない。旧データに残るプロパティは読み込み時に無視し、通常の保存が行われた場合は現行スキーマから落ちてよい。

併せて、ロールプレイで会話中に変化した公開状態を次ターンへ反映する。

1. 直近会話または要約で明かされた内容を、会話開始時点の未公開状態より優先する。
2. `sessionCanon` を固定 `contextSnapshot` へ書き戻さず、プロンプト構築時に重ねて実効 canon を作る。
3. 通常のバックグラウンド要約でも `sessionCanonItems` を要約・関係性と同じ境界で保存する。
4. 追加のメッセージ単位LLM呼び出しは作らない。fold前は直近会話、fold後は要約と session canon で連続性を保つ。

## 1. 背景

現行の `Character.secrets` は、次の異なる概念を1つの自由記述へ混在させている。

- 普段は表に出しにくい性格
- 本人が意図的に隠している過去や事情
- 作品上まだ公開されていない設定
- 親密度や状況に応じて変わる態度

ロールプレイの人物カードでは、この値を毎ターン次の固定ラベルでモデルへ渡している。

> 見せない面（自分からは明かさず、親密度や状況次第で滲ませる）

`contextSnapshot.character` はセッション開始時に固定されるため、会話中ですでに露見した後も、この指示だけは「まだ明かしていない」前提をモデルへ与え続ける。直近会話や要約に公開済みの事実があっても、固定 system prompt と衝突し、キャラクターが未発覚のように応答する原因になる。

現行には会話状態の更新機構があるが、`secrets` とは接続されていない。

- 全メッセージは会話ログへ即時保存される。
- `conversationSummary`、`relationshipState`、`sessionCanon` は履歴fold時に更新される。
- `relationshipState` は信頼、親密さ、緊張、呼び方、約束、未解決話題を持つが、秘密ごとの公開状態は持たない。
- `sessionCanon` は会話中に明かされた事実を保存できるが、通常の次ターン用プロンプトへ入っていない。
- バックグラウンド要約は `performSummary` から `sessionCanonItems` を受け取っても、`mergeSummaryIfCursorUnchanged` へ渡していない。

このため、「人物の固定属性」と「会話で変わる公開状態」の責任を分離する。

## 2. 決定事項

### 2.1 ユーザー確認済み

- 「見せない面」を特別な設定項目として廃止する。
- 既存データの移行は行わない。
- 先に確認したロールプレイ公開状態の反映漏れと、バックグラウンド要約の session canon 保存漏れを同じ設計で直す。

### 2.2 本設計で固定する方針

- `Character` から `secrets` を削除する。
- 新規セットアップ、設定相談、人物編集、生成プロンプトから `secrets` と「見せない面」を削除する。
- `secret` 旧キーの受け入れと、`traits` の「秘密」「見せない面」を `secrets` へ昇格する互換処理も削除する。
- 「秘密」「見せない面」という trait ラベル自体は禁止しない。通常の trait として入力された場合は、恒久的な非公開命令を付けず、そのまま人物像として扱う。
- 公開ライフサイクルが必要な事実は `LatentCanonItem.status` と evidence で管理する。
- `contextSnapshot` の固定方針は維持する。会話中の状態変化を理由に snapshot を更新しない。
- `sessionCanon` は派生データとして維持し、`RoleplaySessionView` へ本文を返さない既存の非公開契約を維持する。
- プロジェクトへ昇格していない session canon を別セッションへ自動継承しない。
- 1メッセージごとの追加抽出は行わない。

## 3. スコープ

### 3.1 対象

- `Character.secrets` の型、正規化、作成、編集、表示からの削除
- セットアップ用プロンプト・JSON契約からの `secrets` 削除
- AI設定相談・refine の入力、差分、危険度判定からの `secrets` 削除
- 小説生成・ロールプレイ生成プロンプトからの「見せない面」削除
- ロールプレイの実効 canon 構築と公開状態の優先順位
- summary fold への初期 canon 候補と既存 session canon の入力
- バックグラウンド要約での session canon 原子的保存
- 関連する単体・統合・受け入れテスト
- 利用ガイドの人物設定説明の更新

### 3.2 対象外

- 既存 `secrets` の `traits`、`description`、latent canon への変換
- 既存作品を走査する移行スクリプト
- 旧データが存在することを知らせるバナーや移行UI
- session canon のプロジェクトへの自動昇格
- fold前に session canon を作るための追加LLM呼び出し
- `relationshipState` への秘密別フラグ追加
- `knownBy` / `explicitlyUnknownBy` による人物別の知識状態更新
- `contextSnapshot` を会話途中で最新の作品設定へ差し替える機能
- 他セッションへの未昇格 session canon の共有

## 4. 用語と不変条件

- **人物像**: 名前、概要、口調、traits、関係性メモなど、キャラクターを継続して演じるための固定情報。
- **初期 canon**: セッション開始時に `latentCanonSnapshot` へ固定した関連設定。
- **session canon**: その会話で明かされた、示唆された、または確定した設定的事実。
- **実効 canon**: 初期 canon に現在の session canon を重ね、同じ事実の古い公開状態を除いた、次ターン生成用の表示。
- **fold前の状態**: まだ `conversationSummary` / `sessionCanon` へ畳まれていない直近メッセージ。
- **fold後の状態**: `summaryThroughMessageId` までが要約・関係性・session canon に反映済みの状態。

次を不変条件とする。

1. 会話ログが正本であり、summary、relationship、session canon は派生データである。
2. 新しい会話情報は、同じ事実に関する会話開始時点の公開状態より優先される。
3. `contextSnapshot` はセッション開始後に変更しない。
4. `pending` / `stale` な派生記憶を最新状態としてプロンプトへ渡さない。
5. summary と session canon のfold境界は同じ messageId とする。
6. session canon 本文を通常API、通知、一覧へ露出しない。
7. 既存 `secrets` を黙って別の意味へ変換しない。

## 5. `Character.secrets` の廃止

### 5.1 型と保存契約

`Character`、セットアップ用人物型、refine用人物パッチ型から `secrets?: string` を削除する。

`characterSchema` は次のように変更する。

- `secrets` の型検査を削除する。
- `normalizeCharacterForStorage` で `secrets` を出力しない。
- JSONの未知プロパティを理由に人物全体を拒否しない既存方針は維持する。

旧 `characters.json` に `secrets` が残っていても、読み込み結果へコピーしない。ファイルを一括書き換えず、人物設定が次に保存された場合は正規化結果から自然に落ちる。旧セッションの `contextSnapshot.character` に `secrets` が残っていても、prompt builder が参照しないため生成へ影響させない。

保存スキーマのバージョン追加や移行記録は行わない。

### 5.2 セットアップとクイックセットアップ

セットアップの相談、draft patch、commit prompt、JSON例から `secrets` を削除する。

- モデルへ独立した `secrets` キーを要求しない。
- `secret` を旧別名として受け取らない。
- `traits` のラベルが「秘密」「見せない面」でも特別フィールドへ移さない。
- draft の lock 対象から `secrets` を外す。
- 保存済み旧 setup session に `secrets` または `lockedFields: ['secrets']` があっても無視する。

公開時期を管理する必要がある設定は、既存の `latentCanonItems` 生成契約へ出力させる。人物の性格として必要な内容は `description` または自由形式 `traits` に出力させる。

### 5.3 人物設定UI

人物作成・編集画面から次を削除する。

- 「見せない面」入力欄
- 詳細サマリー内の「見せない面」表示
- draft editor の `secrets` state と変更判定
- setup draft change の `secrets` 差分

代替入力欄は追加しない。内面は既存の概要・特徴へ、公開管理が必要な設定は作品設定の未公開設定へ入力する。

### 5.4 設定相談・refine

設定相談のモデル入力、出力正規化、patch card、scan fingerprint、risk policy から `secrets` を削除する。旧モデル出力に `secrets` が含まれても未知フィールドとして無視し、人物更新へ適用しない。

`secrets` の変更を review 扱いにしていたテストは削除または通常の重要人物項目のテストへ置き換える。

### 5.5 生成プロンプト

小説生成の人物一覧とロールプレイの persona card から `secrets` の本文・ラベルを削除する。

次のような恒久指示を別の固定規則へ移してはならない。

- 自分からは明かさない
- 普段の言動には出さない
- 限られた相手にだけ滲ませる

必要な非公開制御は canon の現在状態から導出する。単なる trait は、他の trait と同じ人物像として扱う。

## 6. ロールプレイ公開状態の反映

### 6.1 情報の優先順位

同じ事実について情報が競合する場合、生成時は次の順で新しい状態を優先する。

1. 直近の未foldメッセージ
2. fresh な session canon
3. conversation summary と relationship state
4. セッション開始時の latent canon snapshot

この順序は「system prompt は常に user prompt より強い」という配置上の矛盾を作らないよう、system prompt 内の初期 canon 自体も実効状態へ置き換えて実現する。

加えて固定規則へ、次の意味の短い優先規則を追加する。

> 会話開始時点の設定より、時系列的に後の会話履歴・要約・セッション内設定を現在状態として優先する。会話ですでに知られた事実を、未発覚として扱わない。

この規則により、session canon の抽出前でも直近会話に露見の根拠があれば、その次の応答から公開済みとして扱える。

### 6.2 実効 canon

`contextSnapshot` へ mutable な session canon を追加しない。`buildRoleplaySystemInstructionsWithReport` の入力へ、snapshot と別に現在の session canon を渡す。

```ts
interface RoleplaySystemPromptInput {
  snapshot: RoleplayContextSnapshot;
  sessionCanon?: LatentCanonItem[];
  outputLength?: number;
  hasConversationSummary?: boolean;
}
```

`buildEffectiveRoleplayCanon` を純関数として追加し、次の順で実効 canon を作る。

1. retired を除いた初期 canon をコピーする。
2. session canon に同じ `canonId` の項目があれば、session側の statement、status、epistemicStatus を採用する。`knownBy` / `explicitlyUnknownBy` は本設計では更新せず、初期項目に存在する値だけを保持する。
3. IDが一致しない旧データでは、scope と正規化statementの一致または包含関係をフォールバック照合に使う。両方に subjectCharacterIds がある場合は対象人物の一致も要求する。
4. 一致した初期項目は重複表示せず、session側の項目1件へ置き換える。
5. 会話から新しく生まれた session canon は追加する。
6. session revealed、session foreshadowed、初期 revealed、初期 foreshadowed、初期 provisional の順で採用する。
7. 現行の canon 件数・文字数上限内へ決定的に切り詰める。

表示ラベルは時点を明確にする。

- 初期 provisional: `会話開始時点では未公開`
- 初期 foreshadowed: `会話開始時点で示唆済み`
- session foreshadowed: `この会話で示唆済み`
- session revealed: `この会話で公開済み`
- revealed: `公開済み`

同じ事実へ「未公開」と「公開済み」を同時に表示してはならない。

### 6.3 session canon 抽出時の初期 canon 対応

summary fold のプロンプトへ、既存 session canon だけでなく、まだ session canon に上書きされていない初期 canon 候補も ID 付きで渡す。

`targetCanonId` は次の両方を指せるものとする。

- 既存 session canon の canonId
- `contextSnapshot.latentCanonSnapshot` の canonId

初期 canon の ID が target された場合、`applySessionCanonPatch` は初期項目を session-local にコピーし、同じ canonId のまま新しい status と roleplay-message evidence を付ける。プロジェクト側の canon store は変更しない。

これにより、次回の実効 canon 構築では ID で確実に初期状態を上書きできる。モデルが target ID を返さなかった場合だけ、既存のstatement照合をフォールバックとして使う。

初期 canon は照合候補であり、公開の根拠ではない。summary prompt には「追加する会話内に evidenceExcerpt を取れる根拠がある項目だけを出力し、候補一覧を見ただけで公開・示唆済みにしない」と明記する。サーバー側でも、空白と改行を正規化した evidenceExcerpt が同じく正規化したfold対象本文の部分文字列にならない初期 canon の状態変更を採用しない。

通常の増分foldでは公開状態を後退させない。既存の revealed を後続出力の foreshadowed で上書きせず、複数evidenceの最も進んだ状態を維持する。過去発言編集後の全文再構築だけは旧派生データを捨てて会話ログから再計算するため、根拠が消えた結果としての降格・消滅を許可する。

追加の抽出呼び出しは増やさず、現在の summary JSON に含まれる `sessionCanon` 配列を利用する。

summary JSON の `sessionCanon` プロパティは、項目が無い場合も空配列で必須とする。プロパティ欠落、配列以外、構造化JSON全体の破損は summary 成功として扱わない。summary だけを先へ進めると、同じfold区間の session canon 抽出機会を失うためである。配列内の一部の不正項目だけは捨て、有効項目と空配列を許可する。

本設計は「会話内で公開・示唆されたか」を扱い、「どの登場人物が知ったか」は更新しない。ユーザーペルソナは CharacterId を持たないため、既存の `knownBy` へ無理に対応づけない。

### 6.4 fold前の会話

設計上、直近メッセージは session canon へ即時反映されない。この遅延は維持する。

- fold前: 生の直近会話と 6.1 の優先規則で公開済み状態を判断する。
- fold後: conversation summary、relationship state、session canon へ引き継ぐ。

fold前に「作品設定へ残す」を押した場合の明示抽出経路は既存設計を維持し、本設計では変更しない。

### 6.5 バックグラウンド要約の保存漏れ

`runBackgroundSummary` は `performSummary` の成功結果を `mergeSummaryIfCursorUnchanged` へ渡す際、次をすべて同時に渡す。

- `conversationSummary`
- `summaryThroughMessageId`
- `relationshipState`
- `sessionCanonItems`

現行のバックグラウンド経路で欠けている `sessionCanonItems: outcome.sessionCanonItems` を追加する。

保存は既存どおりセッションロック内で、expected cursor と expected revision が一致する場合だけ行う。summary、relationship、session canon、両カーソル、`derivedMemoryStatus` を1回の安全書き込みで更新し、一部だけ進んだ状態を作らない。

同期要約、バックグラウンド要約、手動編集後の記憶再構築で、同じ merge 契約を共有する。経路ごとの引数漏れを防ぐため、可能なら成功 outcome をそのまま受ける共通関数へ寄せる。

## 7. データとAPI契約

### 7.1 Character

```ts
interface Character {
  characterId: CharacterId;
  name: string;
  aliases?: string[];
  role: CharacterRole;
  description: string;
  speechStyle?: string;
  relationshipNotes?: string;
  traits?: CharacterTrait[];
  currentState?: string;
  greeting?: string;
  dialogueExamples?: string[];
}
```

`secrets` は deprecated として型へ残さず、完全に削除する。

### 7.2 RoleplaySession

保存形状は原則として変更しない。`sessionCanon` は既存の `LatentCanonItem[]` を維持する。初期 canon に対応する session item は、同じ canonId と session-local evidence を持つ。

`RoleplaySessionView` は引き続き `contextSnapshot` と `sessionCanon` 本文を除外し、件数・カテゴリ・opaque ID だけを返す。

### 7.3 旧データ

- 旧 `characters.json` の `secrets`: 無視する。
- 旧 setup session の `secrets` / `secret`: 無視する。
- 旧 `lockedFields` の `secrets`: 無視する。
- 旧 roleplay snapshot 内の `character.secrets`: 無視する。
- `sessionCanon` が無い旧セッション: 空配列として扱う。
- 初期 canon と別IDで保存された旧 session canon: statementフォールバックで実効表示を重複排除する。

変換・警告・バックアップファイル生成は行わない。

## 8. プロンプト予算

session canon を追加枠として無制限に積まず、既存の `roleplay.contractCanon` セクション内で初期 canon とまとめて予算配分する。

- hard contract の最低予約を維持する。
- session revealed を初期 provisional より優先する。
- statement を途中で切って意味を変えず、項目単位で落とす。
- 省略結果は既存の `PromptBudgetReport` へ記録する。
- session canon 本文を新しい診断DTOや通知へ複製しない。

件数上限は既存の関連 canon 最大12件を維持し、実装時の実測で不足が確認されるまで増やさない。

## 9. 競合・失敗時の扱い

- summary LLM が `sessionCanon` 配列を返さない場合、summary本文があっても構造化結果を不成立とし、fold境界を進めない。バックグラウンド経路はログを残して終了し、次回送信時の同期要約は既存の `summary_failed` を返す。
- session canon の1項目だけが不正なら、その項目だけを捨て、他の有効項目とsummaryを使う。
- expected cursor または revision が変わった background job は保存せず破棄する。
- derived memory が `pending` または `stale` の間は生成を既存どおりブロックし、古い session canon を現在状態として使わない。
- session canon と初期 canon のフォールバック照合が曖昧な場合は、誤上書きせず別項目として残す。ID一致を最優先する。
- プロンプト予算に収まらない場合は公開済み session canon を優先し、それでも不可能なら既存の明示的な budget error を返す。

## 10. セキュリティと非公開境界

本設計で非公開情報の送信範囲は広げない。latent canon と session canon は、生成に必要な範囲で選択したLLM事業者へ送信され得る既存仕様を維持する。

- 通常の roleplay session API に session canon 本文を追加しない。
- shielded UI で statement や evidence excerpt を返さない。
- prompt dump には実際に送信した canon が含まれ得る既存注意を維持する。
- 通知、budget report、通常エラーへ canon 本文を含めない。
- `Character.secrets` の削除によって旧値をログや警告へ転載しない。

## 12. テスト計画

### 12.1 secrets 廃止

1. `Character` と各patch型に `secrets` が存在しない。
2. 旧JSONに `secrets` があっても人物は読み込め、正規化結果には含まれない。
3. 旧 setup JSON の `secrets` / `secret` / locked field を無視する。
4. setup prompt と commit prompt が `secrets` キーを要求しない。
5. trait ラベル「秘密」「見せない面」を独立項目へ昇格しない。
6. 人物設定・setup draft・refine patch card に「見せない面」入力や表示がない。
7. 小説生成とロールプレイ生成のプロンプトへ旧 `secrets` 本文・ラベルが入らない。
8. description、traits、口調、関係性メモなど他の人物項目は従来どおり入る。

### 12.2 公開状態

9. 直近会話で秘密が明かされた場合、次ターンのプロンプトに「すでに知られた事実を未発覚として扱わない」規則が入る。
10. 初期 canon が provisional、対応する session canon が revealed の場合、実効 canon には公開済み項目だけが1件入る。
11. session canon が foreshadowed の場合、初期未公開との二重表示をせず「この会話で示唆済み」となる。
12. ID不一致の旧sessionでも、scope・subject・statement一致なら重複排除できる。
13. 曖昧な別事実は誤って統合しない。
14. 会話由来の新規 session canon が次ターンのsystem promptへ入る。
15. retired item はプロンプトへ入らない。
16. session canon 追加後も prompt budget report と上限が維持される。

### 12.3 summary と保存

17. 同期要約成功時、summary、relationship、session canon、両カーソルが同じ境界へ進む。
18. バックグラウンド要約成功時も同じ4要素が保存される。
19. バックグラウンド要約の stale job は summary と session canon のどちらも保存しない。
20. 要約結果に `sessionCanon` 配列が無い場合、summary・session canon・両カーソルのどれも進めない。
21. 初期 canon ID を target した抽出は同じIDの session-local itemを作る。
22. 初期 canon 候補だけでは公開状態を更新せず、fold対象会話内のevidenceが必要になる。
23. 増分foldで revealed が foreshadowed へ降格しない。
24. `knownBy` / `explicitlyUnknownBy` は本設計のfoldで新規推定・更新されない。
25. fold前の直近会話は従来どおり次ターンへ入り、追加LLM呼び出しは発生しない。
26. pending / stale memory 中は古い session canon を使って生成しない。

### 12.4 非公開境界

27. `RoleplaySessionView` に `contextSnapshot`、session canon本文、旧 `secrets` が含まれない。
28. shielded summary、通知、通常エラーへ canon statement と evidence が含まれない。
29. reveal API と promote API の明示操作は従来どおり機能する。

## 13. 受け入れシナリオ

### 13.1 直近会話で露見する

1. 未公開設定に、対象人物が隠している過去を登録する。
2. ロールプレイを開始する。
3. ユーザーが会話内でその過去を知り、キャラクターも知られたことを認識するやり取りを行う。
4. 直後にその件へ触れる。

判定: キャラクターは未発覚としてごまかさず、知られた後の反応を返す。fold完了を待つ必要はない。

### 13.2 fold後も公開状態を保つ

1. 13.1 の会話を要約閾値まで続ける。
2. 対象の露見場面が直近40件から外れた後、再びその件へ触れる。

判定: conversation summary と session canon により、公開済み状態が維持される。初期 canon の「未公開」と同時にプロンプトへ出ない。

### 13.3 バックグラウンド要約

1. 通常ターン完了後のバックグラウンド要約を発火させる。
2. summary fold が session canon 項目を返す。
3. セッションを再読込し、次のターンを送る。

判定: session canon と `sessionCanonThroughMessageId` が summary と同じ境界で保存され、次ターンへ反映される。

### 13.4 旧データ

1. `Character.secrets` を含む旧 `characters.json` と旧 roleplay snapshot を読み込む。
2. 人物設定画面とロールプレイを開く。

判定: 読み込みエラーにならず、「見せない面」は表示・生成プロンプトへ現れない。自動移行や警告も発生しない。

## 14. 実装順序

1. `Character` と共有正規化から `secrets` を削除し、旧JSON無視の契約テストを追加する。
2. setup、commit、draft patch、refine の型・プロンプト・正規化を削除する。
3. 人物設定・setup・refine UI から入力・表示・差分判定を削除する。
4. 小説・ロールプレイ生成プロンプトから `secrets` を削除する。
5. 実効 canon 純関数とプロンプト優先規則を追加する。
6. summary prompt へ初期 canon 候補を渡し、同一IDの session-local 上書きを実装する。
7. バックグラウンド要約の `sessionCanonItems` 引き渡しを修正し、3経路のmerge契約を共通化する。
8. 単体・統合・受け入れテストを実施する。
9. 利用ガイドとリリースノートを更新する。
